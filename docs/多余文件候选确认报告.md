# 多余文件候选确认报告

本报告对应 Issue #86。它只做候选确认，不做清理落地。本轮不删除、不移动、不归档，先把引用关系、生成关系、原始候选类别和人工确认边界分清楚。

说明：

- 本表不构成删除授权。
- 原始候选类别按 Issue 中的 `archive_candidate` / `delete_candidate` / `needs_human_confirmation` 记录。
- `additional_candidate` 仅作为后续扩展占位，本轮没有单列到候选表里。

## 1. 总体结论

本轮扫描后，可以把候选文件分成三类：

1. 明确应保留的文件。
2. 可以进入下一轮小 PR 继续处理的文件。
3. 需要人工确认后再决定是否归档、合并或删除的文件。

结论上，`exports/markdown_views/第五项B三人试点对象锚点视图.md` 和 `data/events.jsonl` 不能按候选直接处理，因为它们都能在现有脚本或测试中找到引用。其余候选里，历史审计类文档更适合走 `archive_later_low_or_medium_risk`，正式定档草案类文件更适合走 `delete_later_requires_final_reference_check`，而批次文件和前置说明则需要先做人工比对，确认是否已经被 canonical 主表吸收。

## 2. 扫描方法

本轮只做静态扫描，不运行任何会批量重写导出文件的命令。扫描分四步：

1. 读取仓库级约束文件 `AGENTS.md`，确认 issue 范围和禁止事项。
2. 检查与导出相关的脚本和测试，重点看 `scripts/export_md.py`、`scripts/export_i5b_auto_adjudication.py`、`tests/test_search_logs_export.py` 里是否有直接引用。
3. 对 issue86 列出的候选文件做全文检索，判断它们是 `referenced`、`not_referenced`、`generated_by_script` 还是 `unknown`。
4. 交叉对照候选文件内容中的状态字段，例如 `batch_pending_merge`、`lead_needs_source_review`、`provisional`，判断它们更适合 `keep`、`archive_later_low_or_medium_risk`、`delete_later_requires_final_reference_check`、`merge_then_archive` 还是 `needs_human_confirmation_before_any_cleanup`。

本轮只确认边界，不对评分、正式结论、总榜或导出结构做任何改写。

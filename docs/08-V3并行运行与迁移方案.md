# V3 并行运行与迁移方案

> 状态：`review_ready`  
> 原则：V4 先证明自己，不以停掉 V3 作为进度。

## 1. 隔离

V3 与 V4 必须分别拥有：

- 数据库/Schema；
- 任务队列；
- worker 服务；
- runtime 目录；
- 环境变量与凭据；
- 发布包；
- 审计目录。

V4 不获得 V3 生产写权限。只读对照也应通过专门账号或导出快照完成。

## 2. V3 资产分类

### 可作只读对照

- 已回源 passage；
- 失败和边界样本；
- 人工 review 结论；
- 重复、错绑、漏链和性能审计；
- 当前生产结果用于 shadow 差异。

### 需要重新验证

- 人物别名和 canonical 映射；
- 重要事件清单；
- 规则有限值；
- 人物画像；
- 史源候选。

### 禁止直接迁移为 V4 正式数据

- claim/material/binding/judgment/score 行；
- V3 自增 ID；
- worker/task 状态；
- 旧缓存命中结果；
- 未重新回源的模型输出；
- V3 正式分和排名。

## 3. 阶段

### P0 文档与契约

当前阶段。无实现、无数据库、无生产权限。

### P1 最小 Schema 与本地契约测试

只实现首条纵切所需对象：

```text
source document/passages
assertions
canonical persons
episodes/participants/evidence links
rule projections
judgments
score contributions
stage jobs/outbox
```

### P2 离线三人纵切

使用冻结输入离线运行，建立 gold metrics 和失败恢复。

### P3 Shadow 数据链

V4 从独立输入生成结果；V3 只作为对照。禁止双写 V3 表。

### P4 Shadow 业务评审

逐事件和逐贡献比较，完成差异裁定与成本报告。

### P5 切换设计

只有全部 Gate pass 后才设计：

- 数据迁移；
- 读写切换；
- 回滚；
- 监控；
- 冻结窗口。

P5 不是自动切换授权。

## 4. Shadow comparison 单位

比较单位应是：

- source family；
- gold episode；
- canonical person；
- rule projection；
- judgment；
- score contribution；
- final rule signal。

不能只比较最终一个分数，否则无法知道差异来自召回、事件身份、规则还是公式。

## 5. 迁移原则

- V4 重新生成自己的稳定 ID；
- 需要引用 V3 时保存 `legacy_reference`，不复用主键；
- 每条迁移记录写明来源、重新验证状态和接受人；
- 不能验证的旧数据留在 V3；
- 生产切换后 V3 先进入只读观察期，不立即删除。

## 6. 回滚

切换设计必须支持：

- 路由回 V3 只读/生产路径；
- 停止 V4 worker；
- 保留 V4 已写数据用于审计；
- 不反向把 V4 半成品写进 V3；
- 清晰区分业务回滚与数据删除。

## 7. V3 维护边界

V3 在 V4 shadow 期间只接受：

- 严重数据错误；
- 安全问题；
- 生产运行故障；
- 为稳定对照所必需的最小修复。

不再扩展 V3 业务链、规则范围或架构层。任何新能力优先在 V4 设计。

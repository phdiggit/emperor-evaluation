# V3 并行运行与迁移方案

> 状态：`v3_retired_readonly_reference`
> 原则：V3 已废弃，只保留为可查询的迁移、回归和差异诊断来源；V4 不回流 V3 运行链。

## 1. 隔离

V3 与 V4 必须分别拥有：

- 数据库/Schema；
- 任务队列；
- worker 服务；
- runtime 目录；
- 环境变量与凭据；
- 发布包；
- 审计目录。

V4 不获得 V3 写权限。可直接使用 `.env` 中已配置的 V3 DSN 进行只读查询；长期复用或进入 V4 合同时，应导出带版本、源行指纹与 lineage 的快照，不让 V4 runtime 依赖 V3 实时状态。

## 2. V3 资产分类

### 可作只读对照

- 已回源 passage；
- 失败和边界样本；
- 人工 review 结论；
- 重复、错绑、漏链和性能审计；
- 当前生产结果用于 shadow 差异。

### 需要重新验证

- 人物别名和 canonical 映射；
- 重要事件清单；
- 规则有限值；
- 人物画像；
- 史源候选。

### 禁止直接迁移为 V4 正式数据

- claim/material/binding/judgment/score 行；
- V3 自增 ID；
- worker/task 状态；
- 旧缓存命中结果；
- 未重新回源的模型输出；
- V3 正式分和排名。

### Claim候选试迁

V3 Claim 的抽取语义可以作为V4候选库存复用，但必须以只读冻结包进入。首批李世民试迁保留Claim、canonical event、证据slice、对象身份提示和V3 route hint；不导出运行路径、自增ID、旧Judgment、材料分或排名。V3 route/binding只能决定复核优先级，不能成为V4规则判断。

只有完成V4 SourcePassage重绑、人物身份确认、跨Claim事件去重、PassageSupport字段审查和规则适用性处置后，候选才可进入Assertion接受Gate。迁移本身不得改变皇帝—rule的`historical_coverage_status`。

李世民首批分层采用固定的“稀缺rule优先、每rule八条、人物与动作类型多样性轮询”排程，形成32个不同Claim的source-rebind队列。V3 Claim confidence只用于同层排程tie-breaker，不是V4业务分；所有未入首批者进入deferred、blocked或unrouted库存，丢弃数固定为0。同一Claim若有多个rule hint只回源一次，但每条rule仍须独立完成适用性、方向和因子语义复核。

V3 `CEK-*` 与V4工作集事件标识不在同一命名空间，标识精确碰撞为0不能解释为没有重复。当前人工审计另识别23条Claim、42个rule-slot属于既有聚合事件的组成部件，其中任用授权与容才共享十九条魏徵纳谏Claim；这类`aggregate_component`只触发人工去重和主结算归属复核，不得自动删除、合并或继承既有Gold。

首批32条规则级预审的处置为：4条新事件候选待V4回源、2条既有聚合部件待去重、6条跨rule主结算、14条错误路由、5条适用性不足、1条史源不足。V3 route的主要误差不是随机噪声，而是可定位的词面触发：反任人唯亲会把“党项、乡党、亲礼、无朋党”误当关系网络，容才会把“诛、杀、斩、贬、免、保全”误当人才安全事件，识才会把荐举后的升迁和使用反馈误当首次发现。后续候选生成必须先检查规则前提和事件所有权，再使用这些关键词召回。

### 人物画像首批冻结迁移包

`eval/v3_person_profile_migration/source_snapshot.json` 是 V3 人物画像的只读来源快照，不是 V4 正式人物画像。其准入条件固定为人物身份 `active`、画像审核 `accepted`、画像就绪 `profile_complete`，同时要求两条 typed axis 完整并存在 accepted authority lineage。

该包保留 V3 人才等级版本分区和独立负面政治影响轴，不把 v2、v4、v5 静默混成同一可比 cohort。V3 自增 ID、旧分数、排名、raw path 和 cache root 均不进入 V4 稳定身份；原始 `profile_payload` 只以 SHA-256 绑定，权威语义来自 typed columns 与 `person_profile_claim_links → claim_cache → claim_evidence → claim_source_slices`。

用户已明确授权 V3 typed 人才等级与政治风险为本轮画像事实源。迁移因此统一分配新的 V4 `PER-V4-*` identity，旧 `P-* / PER-*` 只保留为 legacy refs，不再二选一。242 个 `active + accepted + profile_complete` 来源身份及画像已全部迁入；11名 V3 缺失者另以可定位史料和 `talent-grade-v5` 守门员规则形成版本化补充画像，合计253份。现有44份 V3 团队画像和11份补充画像保留独立人工能力域；其余198份因 V3 没有结构化能力域，保存空数组并明确解释为“未评审、未断言”，不得解释为没有能力，也不得在未补能力域前进入团队窗口。完整结果见 `eval/v3_person_profile_migration/migration_report.json`。

V4 PostgreSQL 持久化使用独立 `v4_person_profile` schema，包含 `import_batches`、`person_identity_registry`、`person_legacy_refs`、`person_profile_snapshots`、`person_profile_lineage`、`person_profile_catalog`、`ruler_team_window_snapshots`、`ruler_team_window_members`。底层快照保持规范化和不可变；`person_profile_catalog` 是同样不可变的一行可读投影，直接保存姓名、人才档位及完整依据、负面政治风险状态/档位及完整依据、版本、置信度和覆盖度，不要求消费方自行 JOIN 或翻查 JSON。全量253份画像、增量写入和零写重跑证据见 `eval/v3_person_profile_migration/postgres_full_profile_import_report.json`。

## 3. 阶段

### P0 文档与契约

当前阶段。无实现、无数据库、无生产权限。

### P1 最小 Schema 与本地契约测试

只实现首条纵切所需对象：

```text
source document/passages
assertions
canonical persons
episodes/participants/evidence links
rule projections
judgments
score contributions
stage jobs/outbox
```

### P2 离线三人纵切

使用冻结输入离线运行，建立 gold metrics 和失败恢复。

### P3 Shadow 数据链

V4 从独立输入生成结果；V3 只作为对照。禁止双写 V3 表。

### P4 Shadow 业务评审

逐事件和逐贡献比较，完成差异裁定与成本报告。

### P5 切换设计

只有全部 Gate pass 后才设计：

- 数据迁移；
- 读写切换；
- 回滚；
- 监控；
- 冻结窗口。

P5 不是自动切换授权。

## 4. Shadow comparison 单位

比较单位应是：

- source family；
- gold episode；
- canonical person；
- rule projection；
- judgment；
- score contribution；
- final rule signal。

不能只比较最终一个分数，否则无法知道差异来自召回、事件身份、规则还是公式。

## 5. 迁移原则

- V4 重新生成自己的稳定 ID；
- 需要引用 V3 时保存 `legacy_reference`，不复用主键；
- 每条迁移记录写明来源、重新验证状态和接受人；
- 不能验证的旧数据留在 V3；
- 生产切换后 V3 先进入只读观察期，不立即删除。

## 6. 回滚

切换设计必须支持：

- 路由回 V3 只读/生产路径；
- 停止 V4 worker；
- 保留 V4 已写数据用于审计；
- 不反向把 V4 半成品写进 V3；
- 清晰区分业务回滚与数据删除。

## 7. V3 维护边界

V3 在 V4 shadow 期间只接受：

- 严重数据错误；
- 安全问题；
- 生产运行故障；
- 为稳定对照所必需的最小修复。

不再扩展 V3 业务链、规则范围或架构层。任何新能力优先在 V4 设计。

# V4 领域模型

> 状态：`accepted`
> 原则：领域对象表达业务事实，表结构和服务实现不得反向定义业务。

## 1. 总览

```text
SourceDocument
  └─ SourcePassage
       └─ Assertion
            └─ EpisodeReconciliation
                 └─ HistoricalEpisode
                      ├─ EpisodeParticipant → CanonicalPerson
                      ├─ EpisodeEvidenceLink → Assertion
                      └─ RuleProjection
                           └─ Judgment
                                └─ ScoreContribution
```

任务与审计对象围绕该链路存在，但不替代业务对象。

## 2. 史源对象

### 2.1 SourceDocument

表示一份可识别、可版本化的史源文献或权威版本。

核心字段：

- `source_document_id`
- `work_identity`：原书身份
- `edition_identity`：版本/承载版本
- `title`
- `source_role`
- `canonical_locator`
- `content_hash`
- `retrieval_provenance`
- `source_status`

同一原书的不同版本可以是不同 SourceDocument，但应共享可比较的 `work_identity`。

### 2.2 SourcePassage

表示可定位、具备足够上下文的不可变史料片段。

核心字段：

- `source_passage_id`
- `source_document_id`
- `locator`
- `raw_text`
- `context_before` / `context_after`
- `content_hash`
- `content_version`
- `section_id` / `section_heading`
- `span_start` / `span_end`
- `passage_kind`
- `linked_passages`
- `overlap_group`
- `window_policy_version`
- `passage_version`
- `acceptance_status`

不得用模型摘要替代 `raw_text`。任命、职责、结果相隔较远时，以同一文档内容版本内的显式
`linked_passages` 保留关系；页面导航等噪声不得进入 Assertion 输入。

## 3. 断言对象

### 3.1 Assertion

表示“某一来源片段声称了什么”，不是 V4 已接受的历史事实本身。

核心字段：

- `assertion_id`
- `source_passage_id`
- `assertion_type`
- `subject_ref`
- `predicate`
- `object_ref`
- `time_expression`
- `location_expression`
- `qualifiers`
- `polarity`
- `source_attribution`
- `extraction_provenance`
- `assertion_status`

Assertion 可以互相支持、冲突或只提供背景。

### 3.2 AssertionRelation

表达断言之间的关系：

- `supports`
- `contradicts`
- `duplicates_expression`
- `narrows`
- `broadens`
- `context_for`
- `same_source_restatement`

关系本身保存当前值并可审查；历史变化由 Git 承担。

## 4. 人物与身份

### 4.1 CanonicalPerson

全局唯一的人物主体。

核心字段：

- `person_id`
- `canonical_name`
- `identity_fingerprint`
- `identity_status`
- `created_from`

“早期”“晚期”“某朝任用”等不得进入 canonical name。

### 4.2 PersonName

保存本名、字、号、爵号、庙号、谥号、异体和检索别名；别名是查找关系，不是新人物。

### 4.3 PersonContext

表达人物在某一政权、皇帝、时期或制度中的上下文：

- 任职时期；
- 政权归属；
- 与皇帝关系；
- 角色阶段；
- 活动时间范围。

人物上下文不得拆成新的 CanonicalPerson。

## 5. HistoricalEpisode

HistoricalEpisode 是 V4 的第一语义工作单元，表示一个可被多来源共同描述、具有相对稳定主体、单一决策或任务责任链与时空边界的原子历史事件。跨多年仕进弧线、多个独立任命、任命与后续撤任不得压成一个 HistoricalEpisode；它们由 EpisodeRelation 连接。

核心字段：

- `episode_id`
- `episode_type`
- `evaluation_context`
- `primary_actor_refs`
- `time_span`
- `location_scope`
- `action`
- `responsibility`
- `outcome`
- `consequence`
- `semantic_fingerprint`
- `episode_status`
- `completeness`
- `uncertainties`

episode 的标题和摘要是显示字段，不参与稳定身份的唯一来源。

### 5.1 EpisodeParticipant

显式表达人物与事件的角色：

- `ruler`
- `appointer`
- `delegate`
- `office_holder`
- `commander`
- `advisor`
- `beneficiary`
- `opponent`
- `victim`
- `source_speaker`
- 其他受控角色。

同一人物可以在同一事件中有多个角色，但规则投影必须选择与当前规则相关的角色。

### 5.2 EpisodeEvidenceLink

把 Assertion 挂到 episode，并标明：

- 支持哪一字段；
- 关系是支持、反驳还是背景；
- 是否为 representative evidence；
- 证据接受状态；
- 当前证据接受状态。

### 5.3 EpisodeRelation

EpisodeRelation 表达两个原子事件之间的阶段、升迁、续权、撤权、结果或因果联系。关系本身保留当前类型、方向、证据和置信度，不进入任一 episode 的语义身份，也不得把不同责任主体重新揉成一个 action。

## 6. 规则对象

### 6.0 RuleEvidenceUnitDraft

规则可以先把多个相关 episode 与 relation 聚合为 RuleEvidenceUnitDraft。它属于规则消费层，只说明当前规则要共同观察哪些事实，不修改 episode，不是 Judgment，也不得直接给分。

RuleEvidenceUnit 以稳定 `unit_code` 保存当前值。成员或决策弧变化时更新 semantic fingerprint；相同输入零写入。不得用新 fingerprint 重新生成 unit code，也不得让同一 Episode 在同一 rule/evaluation context 下跨单元重复消费。

### 6.1 RuleDefinition

规则的当前业务定义，包括：

- `rule_code`
- `input_type`
- `applicability`
- `coverage_unit`
- `dedupe_key`
- `scoring_unit`
- `factor_schema`

### 6.2 RuleProjection

把中立业务对象投影到某条规则：

```text
episode/person/aggregate_context/governance_achievement
× rule_code
→ rule_projection
```

Projection 只说明“该对象如何被当前规则观察”，不直接给分。

### 6.3 Judgment

对 Projection 的结构化裁量：

- 是否适用；
- 方向；
- 有限值因子；
- 归因；
- 证据充分性；
- 不确定性；
- 复核状态；

### 6.4 ScoreContribution

由已接受 Judgment 和确定性公式生成。不得由模型直接输出。

## 7. 人物集合与快照

### 7.1 PersonProfileSnapshot

规则使用人物能力或风险信息时读取已冻结的当前画像；相同人物只保留一条当前值，历史由 Git 承担。

### 7.2 RulerPersonSetSnapshot

用于 `team_building` 等人物集合型规则：

- 评估皇帝；
- 评估时间窗；
- canonical person 集合；
- 人物角色；
- 画像冻结依据；
- 纳入/排除理由；

### 7.3 ObjectResearchProfileSnapshot

保存权威学术研究对人物、制度或政策对象的当前总结，用于检索扩展、原始史料定位和 Judge 背景。人物对象引用 `CanonicalPerson`；制度、政策在正式身份建立前使用显式候选对象引用。

核心字段：

- `profile_ref`；
- `subject_ref`、`subject_kind`；
- 规范化学术总结与争议点；
- 学者、论著、出版物、页码或稳定链接；
- 原始史料定位和已关联 Assertion；
- 检索词与允许使用范围。

学术总结不得直接接受为 V4 正式事实、选择计分因子或生成 ScoreContribution。完成原始史料定位后，正式事实仍进入 `SourcePassage → Assertion → HistoricalEpisode` 链。

制度、政策及文官治理产出查询必须先生成 `ScholarGuidedRetrievalTask`，再依次进入版本化 Source Cache 和候选 Judge；普通人物事件已有直接原始史料定位时可以跳过学术检索。任务按 rule 声明机制谓词，不能把纳谏的“表达安全”谓词套用到任用授权、团队建设或制度落实。候选冻结门禁必须核对每个任务已绑定 Source Cache 与 Judge，缺一即失败关闭。

## 8. 任务与审计对象

- `PipelineRun`
- `StageJob`
- `OutboxEvent`
- `Artifact`
- `ReviewDecision`
- `CoverageReport`
- `ReleaseGateDecision`

它们记录处理状态，不应被用作历史事实。

## 9. 身份与版本原则

- 稳定 ID 不由可变摘要、数据库自增 ID 或模型措辞单独决定。
- fingerprint 是候选匹配工具，不是自动合并的充分条件。
- 合并与拆分都生成新版本和 lineage。
- 退役对象保留审计关系，不继续进入活动消费。
- 物理表可以重构，领域身份和版本关系必须保持。

# 史源数据平台实现设计

## 1. 状态与适用范围

状态：已采纳，作为实现设计口径使用。

本设计是 #236 的实现口径收口，承接《史源数据平台架构决策.md》的架构结论，供后续 PostgreSQL schema、RabbitMQ worker skeleton、outbox dispatcher、Wikisource 最小采集试点和 JSONL 导入 dry-run 使用。

本设计只定义边界、状态机、目标表清单、连接键、索引草案和切库阶段，不写 PostgreSQL schema、不写 migration、不新增 Docker Compose、不安装服务、不写 worker、不写 crawler / parser、不修改 JSONL、不迁移数据。

## 2. 不变的技术选型

- PostgreSQL = 目标主库 / canonical fact source。所有任务事实、史源版本、证据链、导入审计和复核状态最终以 PostgreSQL 为准。
- RabbitMQ = 并发投递和 worker 调度。RabbitMQ 只负责就绪任务通知与分发，不保存 canonical 状态。
- SQLite = 当前本地生成库 / 兼容缓存。现有 `scripts/build/build_db.py`、SQLite build 和 Markdown 导出继续服务本地验证。
- JSONL = 当前事实源。未来切换后，JSONL 只作导出快照、fixture 和历史审计，不再作为长期写入源。
- Redis = 缓存 / 热索引候选，不是 canonical。
- OpenSearch = 增强检索候选，不在第一阶段引入。只有 PostgreSQL FTS + pg_trgm 基准测试不足时再评估。
- MongoDB = 观察备选，不作为第一主库。

## 3. 当前系统边界：JSONL / SQLite / PostgreSQL / RabbitMQ

当前阶段仍是 JSONL 唯一写源，SQLite 由 JSONL 构建，Markdown 由现有导出链生成。文档、现有 SQLite build、现有 JSONL 校验不依赖 PostgreSQL / RabbitMQ。

目标阶段中：

- PostgreSQL 承载事实链、任务状态、导入审计、段落版本、证据链接、候选匹配和复核项。
- RabbitMQ 承载轻消息投递，只发送 `job_id`、`kind`、`schema_ver`、必要 trace 信息，不传递大 payload。
- SQLite 继续作为本地兼容缓存，直到 PostgreSQL 写源切换完成后再降级为小样本或离线导出缓存。
- JSONL 在切库完成后冻结为导出快照、小 fixture 和历史审计材料。

不得设计长期 JSONL + PostgreSQL 双写，也不得设计 `JSONL -> SQLite -> MongoDB` 这类多次搬家路线。

## 4. 并行任务与可靠投递

RabbitMQ 采用至少一次投递语义。失败、超时、连接中断或 worker 崩溃后允许重复投递；正确性来自 PostgreSQL 中的唯一约束、任务状态机和 worker 幂等，而不是队列“只投一次”。

必须遵守以下约束：

- RabbitMQ 不保存 canonical 状态。
- RabbitMQ 只投递 `job_id`、`kind`、`schema_ver` 等轻消息。
- worker 必须幂等，重复消费同一 job 时只能产生同一最终结果或 no-op。
- ACK 必须在 PostgreSQL 结果提交后。
- 使用 manual ACK。
- dispatcher 发布时使用 publisher confirms。
- 使用 DLQ / dead-letter；DLX 优先通过 RabbitMQ policy 管理，不在代码中硬编码大量 `x-arguments`。
- `idem_key` 必须唯一。
- `attempt_count`、`max_attempts`、`next_run_at`、`locked_by`、`locked_at`、`lease_until` 进入 `jobs` 草案。

第一阶段采用统一任务表，不采用多张阶段 job 表：

```text
search_tasks    # 业务意图：要查什么
jobs            # 统一执行任务
job_runs        # 运行尝试记录
job_deps        # 仅在 fan-in/fan-out 需要时使用
outbox          # 事务消息
```

`jobs.kind` 使用短值：

```text
search
fetch
parse
match
draft
review_notify
```

第一阶段不单独建 `index_jobs`。PostgreSQL 内部索引随写入完成；若未来接 OpenSearch，再新增外部索引同步 job。

推荐事务流程：

```text
1. PostgreSQL 事务中创建/更新业务结果、子任务和 outbox。
2. 事务提交。
3. dispatcher 从 outbox 发布 RabbitMQ，并等待 publisher confirm。
4. worker 收到消息后只用 job_id 查询 PostgreSQL。
5. 若 job 已完成，幂等 no-op + ACK。
6. 若未完成，执行任务。
7. 执行结果提交 PostgreSQL 后 ACK。
```

职责边界：

- PostgreSQL `jobs` = 任务事实源。
- PostgreSQL `outbox` = 待发布事件。
- RabbitMQ = 就绪任务通知与分发。

## 5. 任务状态机

`jobs.status` 草案使用以下状态：

```text
queued
ready
running
retry_wait
succeeded
failed
dead_lettered
blocked
cancelled
```

状态约束：

- `queued` 表示依赖尚未满足，通常由 `job_deps` 控制。
- `ready` 表示可被 dispatcher 发布，或等待 `next_run_at` 到期。
- `running` 必须带 `locked_by`、`locked_at`、`lease_until`。
- `retry_wait` 表示失败后等待重试，`attempt_count < max_attempts`。
- `failed` 表示已失败但仍可由人工处理或重新排队。
- `dead_lettered` 表示进入 DLQ 或达到最大尝试次数，需要人工介入。
- `blocked` 表示外部依赖、权限、站点限速或人工复核缺口阻塞。
- `succeeded` 和 `cancelled` 为终态。

`job_runs` 记录每次尝试：开始时间、结束时间、worker、输入摘要、输出摘要、错误类型、错误信息、重试建议和 trace id。`job_runs` 不替代 `jobs` 当前状态，只提供审计历史。

人工介入入口由 `review_items` 或 job 状态承接。达到最大重试次数、DLQ、解析失败、低置信候选、站点策略拒绝、引用链不完整等情况，不直接写成正式证据，先进入复核项。

## 6. 史源文档、版本与快照

史源版本模型拆成四层：

```text
src_hosts
src_docs
doc_revs
passages
```

职责如下：

- `src_hosts`：source host 元信息，例如 Wikisource、ctext、影印站、古籍库。记录 `trust_class`、`base_url`、`adapter`、`rate_limit`、`concurrency_limit`。
- `src_docs`：逻辑文档 / 卷篇身份。记录 source title、work code、volume、canonical URL、source_host。
- `doc_revs`：每次抓取的不可变快照。记录 `sha256`、`object_key`、`mime`、`encoding`、`etag`、`last_modified`、`fetched_at`、`fetch_status`、`parser_ver`、`norm_ver`。
- `passages`：引用 `doc_rev_id`，不只引用 `doc_id`。记录 `seq`、`location`、`raw_text`、`norm_text`、`token_text`、`search_vec`。

原始 HTML / PDF / TXT 不直接塞进 PostgreSQL 大字段。原始快照进入本地内容寻址文件仓库或 S3-compatible object storage，数据库只保存 `object_key`、`sha256`、`mime`、`size` 等元信息。

`previous_passage_id` / `next_passage_id` 不作为第一版字段。上下文窗口通过 `UNIQUE(rev_id, seq)` 和 `seq ± N` 查询。

检索链路必须补 `search_hits`：

```text
search_task -> search_hits -> fetch job -> doc_rev
```

`search_hits` 保存 URL、标题、摘要、排名、source_host、url_hash、处理状态和拒绝原因。没有 `search_hits`，search task 到 source document 中间会断链。

## 7. 中文古文检索方案

第一阶段检索方案不是笼统依赖默认 PostgreSQL FTS，而是：

```text
PostgreSQL 元数据过滤
+ 应用侧中文/古文规范化与分词
+ GIN tsvector
+ pg_trgm 辅助模糊匹配
```

`passages` 预留字段：

```text
raw_text
norm_text
token_text
search_vec
norm_ver
token_ver
```

索引草案：

```text
GIN(search_vec)
GIN(norm_text gin_trgm_ops)
```

限制必须进入后续 benchmark：

- 中文古文无空格，默认 FTS 不可直接假定有效。
- 单字、两字词、异体、繁简转换、人物别名必须做基准测试。
- 对同一人物的名、字、谥号、庙号、旧称、避讳写法和异体词要形成 query_profile 层的别名展开。
- 如果两字词、异体词和复合召回效果不足，后续再评估 OpenSearch。

#241 离线 benchmark 只用人工 fixture 和纯 Python 内存评估固定最低口径：单字、2-3 gram、三字以上直接子串、人物别名、繁简/异体 query 规范化、标点/全角空格/脚注噪音剥离。它不访问公网，不连接 PostgreSQL / RabbitMQ，不生成 evidence card、score、rank 或长期导出文件；结论只能用于决定下一步真实 PostgreSQL FTS / pg_trgm benchmark 的测试入口，不能伪装成生产检索质量结论。



## 9. 表字段类型、连接键和索引草案

ID 策略：

- 数据库内部主键使用 `bigint identity`。
- 外部稳定编码使用 `code TEXT UNIQUE`。
- JSONL / 导出 / 人工审计继续看 `code`。
- 数据库联表用短整数 `id`。

示例：

```text
evd_cards.id = bigint identity
evd_cards.code = EVD-I5B-LIUBANG-...
```

不得用中文 `person`、`item`、`subitem` 作为最终主连接键。第一版新增 `persons`、`person_aliases`、`subitems`，把人工可读名称、别名和子项稳定编码从证据事实里拆出来。

关系表必须包含：

```text
passage_people(passage_id, person_id, role, confidence)
evd_src_links(evd_id, passage_id, role, span_start, span_end)
cluster_evd(cluster_id, evd_id, role)
```

`mentioned_persons` 不应只存 JSON 数组。人物命中、证据引用和证据组成员必须有关系表，才能做反查、去重、复核和索引评估。

外键索引评估草案：

- 所有高频 join 外键默认建普通 btree 索引，包括 `person_aliases.person_id`、`src_docs.host_id`、`doc_revs.doc_id`、`passages.rev_id`、`passage_people.passage_id`、`passage_people.person_id`、`search_tasks.query_profile_id`、`search_hits.search_task_id`、`cand_matches.search_hit_id`、`evd_src_links.evd_id`、`evd_src_links.passage_id`、`cluster_evd.cluster_id`、`cluster_evd.evd_id`、`job_runs.job_id`、`job_deps.job_id`、`job_deps.depends_on_job_id`、`import_rows.import_id`。
- `jobs.idem_key` 建唯一索引。
- `search_hits.url_hash` 建唯一或范围唯一索引，唯一范围至少包含 `source_host` 与规范化 URL hash。
- `passages` 建 `UNIQUE(rev_id, seq)`。
- `evd_cards.code`、`persons.code`、`subitems.code`、`query_profiles.code` 建唯一索引。
- `outbox` 按 `published_at IS NULL`、`next_publish_at`、`event_kind` 设计 dispatcher 查询索引。

字段草案只进入后续 schema PR，不在本 PR 写 SQL。后续 schema PR 必须逐表确认 `NOT NULL`、枚举值、唯一约束、外键级联策略和索引命名。

## 10. thematic anchor 在 PostgreSQL 中的收束方式

当前 SQLite 的三张表：

```text
anchor_objects
anchor_events
anchor_mechanisms
```

可保留为 SQLite 兼容缓存。未来 PostgreSQL 不建议直接复制三张同构表。

建议收束为：

```text
anchors
anchor_links
```

或在语义稳定后拆为：

```text
anchor_evd
anchor_cluster
anchor_person
```

anchor 与 evidence、cluster、person 的直接关系不得继续依赖 `item + subitem` 表示。`item + subitem` 只用于范围过滤，不能替代关系表。

## 11. JSONL 一次切库方案

切库必须是单向阶段流程：

```text
阶段 A：JSONL 唯一写源。
阶段 B：导入 PostgreSQL staging，反复验证。
阶段 C：冻结 JSONL 写入。
阶段 D：全量导入 + 行数 / ID / 引用 / hash 校验。
阶段 E：PostgreSQL 成为唯一写源。
阶段 F：JSONL 只作导出快照、小 fixture 和历史审计。
```

禁止事项：

```text
JSONL 和 PostgreSQL 长期双写。
JSONL -> SQLite -> MongoDB 这类多次搬家。
```

`imports` 记录一次导入批次：来源、开始时间、结束时间、状态、操作者、工具版本、输入 hash、摘要统计和错误摘要。

`import_rows` 记录逐行审计：

```text
source_file
line_no
payload_hash
import_status
target_table
target_id
error
```

导入 dry-run 必须先校验行数、code 唯一性、外部引用、payload hash、目标表映射和错误分布。切换写源前不得让 JSONL 与 PostgreSQL 同时接受长期业务写入。

## 12. 本地开发与测试边界

- 文档、现有 SQLite build、现有 JSONL 校验不依赖 PostgreSQL / RabbitMQ。
- 新增 PostgreSQL / RabbitMQ 测试必须可跳过或使用明确 marker。
- `.env` 不进 Git。
- 未来 Codex 连接本地 LAN PostgreSQL / RabbitMQ 由用户环境提供。
- CI 默认保留纯文档、JSONL 校验和 SQLite build 能力；服务依赖测试必须显式 opt-in。

后续 schema / worker PR 可以新增本地示例配置，但不得在默认验证链里要求安装 PostgreSQL、RabbitMQ、Redis、OpenSearch 或 MongoDB。

# 数据层级与批次文件治理规则

本规则用于约束项目中持续增长的数据文件，避免后续推进多个项目、多人、多轮回源时形成散乱文件堆积。

## 一、核心原则

1. **长期主表少而稳**：长期维护的数据应尽量集中在 canonical JSONL 主表中。
2. **批次文件可追溯但不常驻膨胀**：批次文件用于 PR 审阅、阶段导入和风险隔离，不应无限期替代主表。
3. **临时判断不强制持久化**：临时 query 思路、草稿判断、一次性检索尝试可以不入库；只有会影响后续复用、审计或裁量的内容才持久化。
4. **证据链必须可重建**：正式进入裁量链的材料，必须能从 query_profile/search_log 追溯到 source、evidence_card、evidence_cluster。
5. **正式定档后可清理过渡文件**：正式定档落地表和必要索引已生成后，临时批次文件可删除或归档，但 canonical 主表与正式导出视图应保留。
6. **对象锚点最小化**：人物、指标、空间、机制等对象锚点只用于校准证据权重，不单独扩展为全量平行评分系统。
7. **已处理 correction batch 不得长期悬挂**：若 correction 已合并入 canonical，必须删除、归档或显式标记完成，避免旧口径在仓库内继续残留。

## 二、数据层级

后续 #230/#231 使用以下分类术语：

- `canonical`：长期主表，例如 `data/evidence_cards.jsonl`。
- `canonical_lane`：稳定但按语义分 lane 的主表，例如 thematic anchor object/event/mechanism lane。
- `active_batch`：当前阶段仍被导出、测试或审计引用的批次。
- `merged_batch`：已合并入 canonical 或 canonical lane 的批次。
- `review_only_batch`：仅保留给人工审阅或 PR 审计的批次。
- `archive_candidate`：归档候选。
- `delete_candidate`：删除候选。

#230 只盘点和打标签；#231 才执行 batch 删除、归档或重组。

### 1. 规则与模板层（长期保留）

路径示例：

- `docs/分项规则/第五项统治者政治素质/B用人与授权.md`
- `docs/证据规则/史料检索与回源工作流.md`
- `docs/证据规则/证据裁量总则.md`
- `docs/数据结构与生成库/批次文件生命周期规则.md`

用途：定义流程、边界、数据结构、裁量方法。

治理要求：

- 数量应少，避免为每个临时任务新增规则文档。
- 若规则已经稳定，应更新既有模板，不另开平行版本。
- 讨论版可保留，但正式执行口径应集中到最新模板或总则中。

### 2. Canonical 数据主表（长期保留）

路径示例：

- `data/query_profiles.jsonl`
- `data/search_logs.jsonl`
- `data/sources.jsonl`
- `data/evidence_cards.jsonl`
- `data/evidence_clusters.jsonl`
- `data/thematic_anchors.jsonl`
- `data/thematic_anchor_objects.jsonl`
- `data/thematic_anchor_events.jsonl`
- `data/thematic_anchor_mechanisms.jsonl`

用途：保存可复用、可检索、可验证的结构化数据。

治理要求：

- 后续正式材料原则上应合并入 canonical 主表。
- 主表是正式数据来源，批次文件不是长期替代品。
- 主表写入前必须确保 JSONL 格式、ID 唯一、引用链完整。
- 人物/theme 聚合锚点继续存入 `data/thematic_anchors.jsonl`。
- 对象、事件、机制等更细粒度锚点若已稳定且需复用，可进入对应的 thematic anchor canonical lane；不扩张为庞大的全量平行评分主表。

### 3. 批次文件层（过渡保留）

路径示例：

- `data/query_profile_batches/*.jsonl`
- `data/search_log_batches/*.jsonl`
- `data/source_batches/*.jsonl`
- `data/evidence_card_batches/*.jsonl`
- `data/evidence_cluster_batches/*.jsonl`

用途：在 PR 审阅、连接器截断风险、多人多轮增量推进时，暂存本轮新增内容。

治理要求：

- 批次文件必须命名清楚：`项目_人物或批次_日期.jsonl`。
- 批次文件只应包含本轮新增内容，不混入无关历史数据。
- 批次文件合并进 canonical 主表后，可删除或移动到归档区。
- 若批次文件长期保留，必须有对应索引或 PR 说明，避免主表与批次文件双轨失控。
- 临时对象池或最小对象锚点可先以批次文件、导出视图或 PR 说明形式存在；稳定后再合并入专题锚点池。
- correction batch 一旦完成合并，不应继续作为活跃执行文件停留在原目录。
- 涉及大量中文史料、证据解释或元数据字段时，批次文件优先使用 UTF-8，无 BOM。
- 批量写入中文 JSONL 时优先使用 Python 生成，写出时明确指定 `encoding="utf-8"`，并在需要保留中文时使用 `ensure_ascii=False`。
- 避免用 PowerShell 直接拼接长中文 JSONL；若必须临时写入，必须回读校验是否出现 `?`、乱码或 BOM。
- 小范围中文字段修补优先用 `apply_patch`，减少中间编码层污染。
- 批次文件合并入 canonical 主表前，必须先通过解析校验和中文回读检查。

#### 批次文件生命周期状态

批次文件在治理上可以先用以下状态描述，不要求立刻写入每个文件的 metadata：

- `active_batch`：当前阶段仍被导出、测试或审计引用。
- `review_only_batch`：仅保留给人工审阅或 PR 审计。
- `merge_pending_batch`：待合并入 canonical 主表。
- `merged_batch`：已经合并入 canonical 主表或 canonical lane，原则上不再作为活跃执行文件。
- `archive_candidate`：归档候选。
- `delete_candidate`：删除候选。
- `needs_human_confirmation`：看似多余但可能是唯一数据源，需人工确认。

状态判断应优先看是否仍被脚本、测试、导出、README 或治理文档引用，而不是只看文件名或日期。

### 4. 导出视图层（阶段保留 / 正式成果保留）

路径示例：

- `exports/markdown_views/*净证据池.md`
- `exports/markdown_views/*裁量复核.md`
- `exports/markdown_views/*自动结算规则敏感点清单.md`
- `exports/markdown_views/*{default_person_group.label}自动结算草案.md`
- `exports/markdown_views/*正式定档落地表.md`

用途：供人工审阅、阶段总结、正式定档。

治理要求：

- 正式定档落地表、净裁量草案、自动结算规则敏感点清单、自动结算草案和人工裁判清单应保留。
- 中间调试导出、临时预览视图可在阶段完成后删除。
- 导出视图不得替代 canonical 数据主表；若两者冲突，以主表和最新正式模板为准。
- 对象锚点导出视图只作为审阅辅助，不得替代证据卡和证据组。
- 正式成果导出与临时/调试导出要区分。
- 后续应支持指定导出，避免全量重写。
- PR 白名单外导出变更必须还原。

### 5. 临时草稿层（可不持久化 / 可删除）

包括：

- 临时 query 思路；
- 一次性搜索尝试；
- 未回源材料的口头判断；
- 尚未决定是否进入 search_log 的散点；
- 为当前对话服务的草稿说明；
- 尚未稳定的对象锚点猜想。

治理要求：

- 不要求持久化。
- 若已经持久化，应标明 `draft`、`lead_only`、`temporary` 或类似状态。
- 正式定档完成后可删除，不影响证据链完整性。

## 三、query_profile 与 search_log 的关系

1. 通用 `query_profile` 定义项目级检索框架。
2. 人物级 `query_profile` 定义某人物在本项目中应查的正向维度、负向维度和相邻项风险。
3. `search_log` 是由 query_profile 派生出的具体检索线索。
4. `search_log` 只保证覆盖入口，不保证每个入口都必须转证据卡。
5. 每个维度可以有多条史料证据，但是否建卡取决于回源质量、直接相关性、新维度价值和裁量必要性。

禁止把人物级 query_profile 当成证据或结论。它只回答：“为什么要查这些方向？”不回答：“这个人应得什么档？”

## 四、证据卡、证据组与对象锚点的关系

1. 证据卡是原子证据，只记录已回源且能归项的材料。
2. 证据组不是新史料，而是对同向、多卡、可裁量材料的结构性合成。
3. 多条同类证据可以增强结构性，但不得按条数机械加分。
4. 同类证据达到代表性覆盖后，后续同类材料只增厚元数据，除非提供新维度、强反证、反转材料或相邻项切分价值。
5. 强正或强负证据组必须接受反向检索和相邻项切分复核。
6. 对象锚点只校准证据权重，不替代 source、evidence_card 或 evidence_cluster，也不直接进入定档。
7. 人才安全处置锚点等对象标签应嵌入证据卡/证据簇层，不应单独演化成多轴笛卡尔积计算。

## 五、清理与归档规则

阶段完成后，按以下顺序清理：

1. 确认批次文件内容已合并入 canonical 主表，或明确决定不合并。
2. 确认正式导出视图已经生成。
3. 删除无用临时草稿、调试导出、重复批次文件。
4. 对有审计价值但不再参与执行的批次文件，可移动到归档区或保留在 PR 历史中。
5. 不删除仍是唯一数据来源的批次文件。
6. 不保留会造成平行评分系统的对象池草稿；只保留已被规则引用或可复用的最小锚点。

删除或归档前必须确认是否唯一数据源。

若文件仍被测试、脚本、导出、README、治理文档引用，不得删除。

对 `archive_candidate` 和 `delete_candidate` 级别的高风险文件，必须单独开 PR，不得混入业务 PR。

第一轮只允许诊断，第二轮才允许小范围归档或删除。

导出视图可删除或归档的前提是能从事实源或批次源重建，或用户明确确认只保留 PR 历史。

## 六、最低追溯链

正式进入定档前，至少应能追溯以下链条：

```text
query_profile
→ search_log
→ source
→ evidence_card
→ evidence_cluster
→ 净证据池/裁量复核
→ 自动结算规则敏感点清单
→ 自动结算草案
→ 定档前人工裁判清单
→ 正式定档落地表
```

如果某一步暂时使用批次文件而非 canonical 主表，应在 PR 或审计视图中说明。

对象锚点若参与证据权重裁量，应能追溯到对应证据卡、证据组或专题锚点；不得脱离证据链单独决定档位。

未来史源上下文平台的最低追溯链扩展为：

```text
query_profile / search_task
→ source_document
→ source_passage
→ evidence_source_link
→ evidence_card
→ evidence_cluster
→ adjudication_decision
→ score_record
```

当前 JSONL 过渡期可暂用 `source_id` 连接 `sources.jsonl` 与 `evidence_cards.jsonl`，但不得把全文上下文塞入 evidence card 来替代 source passage。

## 七、执行口径

- 日常推进允许使用批次文件降低写入风险。
- 阶段收束时必须回到 canonical 主表与正式导出视图。
- 规则文档宁少勿散；数据文件宁结构化勿长篇散文。
- 对象锚点宁少勿全；先服务裁量，再考虑沉淀，不为每个项目预建全量对象库。
- 不展示阶段总榜、不定分、不排名，除非当前流程已经进入正式定档/汇总阶段并且用户明确要求。

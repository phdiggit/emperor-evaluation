# 数据层级与批次文件治理规则

本规则用于约束项目中持续增长的数据文件，避免后续推进多个项目、多人、多轮回源时形成散乱文件堆积。

## 一、核心原则

1. **长期主表少而稳**：长期维护的数据应尽量集中在 canonical JSONL 主表中。
2. **批次文件可追溯但不常驻膨胀**：批次文件用于 PR 审阅、阶段导入和风险隔离，不应无限期替代主表。
3. **临时判断不强制持久化**：临时 query 思路、草稿判断、一次性检索尝试可以不入库；只有会影响后续复用、审计或裁量的内容才持久化。
4. **证据链必须可重建**：正式进入裁量链的材料，必须能从 query_profile/search_log 追溯到 source、evidence_card、evidence_cluster。
5. **正式定档后可清理过渡文件**：正式定档落地表和必要索引已生成后，临时批次文件可删除或归档，但 canonical 主表与正式导出视图应保留。
6. **对象锚点最小化**：人物、指标、空间、机制等对象锚点只用于校准证据权重，不单独扩展为全量平行评分系统。
7. **已处理 correction batch 不得长期悬挂**：若 correction 已合并入 canonical，必须删除、归档或显式标记完成，避免旧口径在仓库内继续残留。

## 二、数据层级

后续 #230/#231 使用以下分类术语：

- `canonical`：长期主表，例如 `data/evidence_cards.jsonl`。
- `canonical_lane`：稳定但按语义分 lane 的主表，例如 thematic anchor object/event/mechanism lane。
- `active_batch`：当前阶段仍被导出、测试或审计引用的批次。
- `merged_batch`：已合并入 canonical 或 canonical lane 的批次。
- `review_only_batch`：仅保留给人工审阅或 PR 审计的批次。
- `archive_candidate`：归档候选。
- `delete_candidate`：删除候选。

#230 只盘点和打标签；#231 才执行 batch 删除、归档或重组。

### 1. 规则与模板层（长期保留）

路径示例：

- `docs/分项规则/第五项统治者政治素质/B用人与授权.md`
- `docs/证据规则/史料检索与回源工作流.md`
- `docs/证据规则/证据裁量总则.md`
- `docs/数据结构与生成库/批次文件生命周期规则.md`

用途：定义流程、边界、数据结构、裁量方法。

治理要求：

- 数量应少，避免为每个临时任务新增规则文档。
- 若规则已经稳定，应更新既有模板，不另开平行版本。
- 讨论版可保留，但正式执行口径应集中到最新模板或总则中。

### 2. Canonical 数据主表（长期保留）

路径示例：

- `data/query_profiles.jsonl`
- `data/search_logs.jsonl`
- `data/sources.jsonl`
- `data/evidence_cards.jsonl`
- `data/evidence_clusters.jsonl`
- `data/thematic_anchors.jsonl`
- `data/thematic_anchor_objects.jsonl`
- `data/thematic_anchor_events.jsonl`
- `data/thematic_anchor_mechanisms.jsonl`

用途：保存可复用、可检索、可验证的结构化数据。

治理要求：

- 后续正式材料原则上应合并入 canonical 主表。
- 主表是正式数据来源，批次文件不是长期替代品。
- 主表写入前必须确保 JSONL 格式、ID 唯一、引用链完整。
- 人物/theme 聚合锚点继续存入 `data/thematic_anchors.jsonl`。
- 对象、事件、机制等更细粒度锚点若已稳定且需复用，可进入对应的 thematic anchor canonical lane；不扩张为庞大的全量平行评分主表。

### 3. 批次文件层（过渡保留）

路径示例：

- `data/query_profile_batches/*.jsonl`
- `data/search_log_batches/*.jsonl`
- `data/source_batches/*.jsonl`
- `data/evidence_card_batches/*.jsonl`
- `data/evidence_cluster_batches/*.jsonl`
- `data/batches/*/source_evidence_specs.jsonl`
- `data/batches/*/source_review_log.jsonl`

用途：在 PR 审阅、连接器截断风险、多人多轮增量推进时，暂存本轮新增内容。

治理要求：

- 批次文件必须命名清楚：`项目_人物或批次_日期.jsonl`。
- 批次文件只应包含本轮新增内容，不混入无关历史数据。
- 批次文件合并进 canonical 主表后，可删除或移动到归档区。
- 若批次文件长期保留，必须有对应索引或 PR 说明，避免主表与批次文件双轨失控。
- 临时对象池或最小对象锚点可先以批次文件、导出视图或 PR 说明形式存在；稳定后再合并入专题锚点池。
- correction batch 一旦完成合并，不应继续作为活跃执行文件停留在原目录。
- 涉及大量中文史料、证据解释或元数据字段时，批次文件优先使用 UTF-8，无 BOM。
- 批量写入中文 JSONL 时优先使用 Python 生成，写出时明确指定 `encoding="utf-8"`，并在需要保留中文时使用 `ensure_ascii=False`。
- 避免用 PowerShell 直接拼接长中文 JSONL；若必须临时写入，必须回读校验是否出现 `?`、乱码或 BOM。
- 小范围中文字段修补优先用 `apply_patch`，减少中间编码层污染。
- 批次文件合并入 canonical 主表前，必须先通过解析校验和中文回读检查。
- 关键词补齐、补搜词、对象锚点扩展和相邻项切分线不得写入 `project_config.yml`；应落在 `source_evidence_specs`、`query_profiles`、`search_logs` 或 `source_review_log`，并能回指具体 `query_profile_id`、`search_id`、source、证据卡或排除理由。

#### 批次文件生命周期状态

批次文件在治理上可以先用以下状态描述，不要求立刻写入每个文件的 metadata：

- `active_batch`：当前阶段仍被导出、测试或审计引用。
- `review_only_batch`：仅保留给人工审阅或 PR 审计。
- `merge_pending_batch`：待合并入 canonical 主表。
- `merged_batch`：已经合并入 canonical 主表或 canonical lane，原则上不再作为活跃执行文件。
- `archive_candidate`：归档候选。
- `delete_candidate`：删除候选。
- `needs_human_confirmation`：看似多余但可能是唯一数据源，需人工确认。

状态判断应优先看是否仍被脚本、测试、导出、README 或治理文档引用，而不是只看文件名或日期。

### 4. 导出视图层（阶段保留 / 正式成果保留）

路径示例：

- `exports/markdown_views/*净证据池.md`
- `exports/markdown_views/*裁量复核.md`
- `exports/markdown_views/*自动结算规则敏感点清单.md`
- `exports/markdown_views/*三人自动结算草案.md`
- `exports/markdown_views/*正式定档落地表.md`

用途：供人工审阅、阶段总结、正式定档。

治理要求：

- 正式定档落地表、净裁量草案、自动结算规则敏感点清单、自动结算草案和人工裁判清单默认先保留在 review-artifact PR；是否进入 canonical branch 必须另行说明。
- 中间调试导出、临时预览视图可在阶段完成后删除。
- 导出视图不得替代 canonical 数据主表；若两者冲突，以主表和最新正式模板为准。
- 对象锚点导出视图只作为审阅辅助，不得替代证据卡和证据组。
- 正式成果导出与临时/调试导出要区分。
- 后续应支持指定导出，避免全量重写。
- PR 白名单外导出变更必须还原。

### 4.1 Canonical PR 与 review-artifact PR branch policy

后续证据批次默认拆成两类 PR：

- canonical branch / mergeable PR：面向 `GPT` 或后续主线，只包含持久研究数据、规则文档、脚本和测试；默认不得包含 `exports/**` 生成物。
- review branch / review PR：分支名使用 `review/*`，可以包含生成的 Markdown exports 供人工或助手审阅。
- review PR 中的 exports 必须显式标记为 derived / review artifact，不得宣称为评分事实源。
- review PR 不直接合并入 canonical branch；若确需把某个导出物长期纳入主线，必须另开 canonical PR 并说明为什么该导出物不能由事实源重建。
- 验证命令若在 canonical 分支生成 `exports/**`，应先记录通过结果，再清理副产物，只保留 `git status`、`git diff --name-only`、`git diff --check` 等范围核对。

### 5. 临时草稿层（可不持久化 / 可删除）

包括：

- 临时 query 思路；
- 一次性搜索尝试；
- 未回源材料的口头判断；
- 尚未决定是否进入 search_log 的散点；
- 为当前对话服务的草稿说明；
- 尚未稳定的对象锚点猜想。

治理要求：

- 不要求持久化。
- 若已经持久化，应标明 `draft`、`lead_only`、`temporary` 或类似状态。
- 正式定档完成后可删除，不影响证据链完整性。

### 6. #376 source/evidence JSONL 布局提案

本小节用于在继续扩展 #366/#369 前，先收束 source/evidence JSONL 的长期位置，避免 `data/batches/` 按人物、子项、批次继续生成大量小 JSONL。

本提案只定义布局和生命周期，不改评分规则，不新增数据库服务，不建立大 registry 框架，不把关键词树写入 `project_config.yml`，也不把 `exports/**` 当作 source/evidence 数据源。

#### Canonical JSONL stores

| Store | 稳定 ID | 负责 | 不负责 |
| --- | --- | --- | --- |
| `data/query_profiles.jsonl` | `query_profile_id` | 项目级、人物级检索画像；正向、负向、反向和相邻项检索维度 | 证据强度、最终裁判、关键词树全量配置 |
| `data/search_logs.jsonl` | `search_id` | 具体检索线索、回源状态、转卡/排除/未决状态、关联 source/evidence ID | 把线索当证据、把未回源 lead 入分 |
| `data/sources.jsonl` | `source_id` | 书目、卷篇、定位、URL 等来源信息 | 长段全文、证据强度、裁判结论 |
| `data/source_packs.jsonl` | `source_pack_id` | 可复用回源包；记录 source locator、短摘、上下文摘要、review 状态和关联 source/search/evidence ID | 替代未来 source passage 全文层；承载每轮批次的重复快照 |
| `data/evidence_cards.jsonl` | `evidence_id` | 已回源、可归项、可裁量的原子证据 | 未回源 lead、证据组结论、最终分数 |
| `data/evidence_clusters.jsonl` | `cluster_id` | 多张原子证据形成的结构性裁量候选 | 新史料、单条证据重复包装、最终档位 |
| `data/thematic_anchors.jsonl` | `anchor_id` | 人物/theme 聚合锚点 | 单独入分、替代证据卡 |
| `data/thematic_anchor_objects.jsonl` | `anchor_id` | 可复用对象锚点，例如人才对象、团队结构、长期网络 | 每条 evidence/search 的重复锚点快照 |
| `data/thematic_anchor_events.jsonl` | `anchor_id` | 可复用事件锚点 | 把事件正证机械累加成档位 |

| `data/query_lane_coverage.jsonl` | `lane_coverage_id` | 每个 batch/person/subitem 的 positive、negative、adjacent query lane 覆盖、转卡、未决和排除理由 | 建证据卡数量目标、评分平衡结论 |

`data/source_packs.jsonl`、`data/object_anchor_coverage.jsonl`、`data/query_lane_coverage.jsonl` 是布局提案中的新增 canonical store 名称。本设计不要求立即迁移旧数据；后续 PR 应按小批次吸收。

#### 未来 PostgreSQL table boundary

当前阶段仍是 JSONL 唯一写源。PostgreSQL 只保留未来 contract，不在本设计中实现 schema、migration、runtime、导入脚本或双写。未来进入 PostgreSQL 原型时，应先走 staging / dry-run / hash 校验，再单向切换写源；不得形成 JSONL 与 PostgreSQL 长期双写。

PostgreSQL 物理表名应使用短名；文档中的逻辑名只用于说明。`source_documents`、`source_passages`、`evidence_source_links` 的物理名可继续对齐现有建议：`src_docs`、`passages`、`evd_src_links`。

| Canonical JSONL store | 未来 PostgreSQL boundary | 进入条件 | 不进入 / reference risk |
| --- | --- | --- | --- |
| `data/query_profiles.jsonl` | `query_profiles` | `query_profile_id` 映射 `query_profiles.code`；项目级和人物级画像进入同表，用 scope/status 区分 | 不保存最终评分；`item/subitem/person` 只做 resolver 输入，不作为最终 join key |
| `data/search_logs.jsonl` | `search_tasks`，必要时派生 `search_hits` | `search_id` 映射 `search_tasks.code`；query text、source scope、lead status、next action 进入任务层 | `linked_source_ids`、`linked_evidence_ids` 必须经 resolver；search log 不是 evidence card |
| `data/query_lane_coverage.jsonl` | `query_profiles` + `search_tasks` 的 coverage 视图或后续轻量 `lane_cov` 表 | 只有当 lane 覆盖需要跨 batch 查询、审计和去重时才建物理表；否则由 `query_profiles/search_tasks` 聚合生成 | 不建关键词树配置表；不把 coverage 解释成评分平衡或建卡配额 |
| `data/sources.jsonl` | `src_hosts`、`src_docs`、`doc_revs`、`passages` | source locator、书目、URL、卷篇和版本信息先进入文档/版本层；短摘和上下文经审核后才成为 passage | `source_id` 不等于 `passage_id`；不能把 evidence card 的 `source_id` 直接当段落外键 |
| `data/source_packs.jsonl` | staging `import_rows` + `src_docs/doc_revs/passages` + `review_items` | 用作 source review packet 的导入输入和审计摘要；稳定 source locator 进入 source/doc/passages 层，待核内容进入 review queue | 不承载全文归档；不替代内容寻址快照或未来 source passage 正文层 |
| `data/evidence_cards.jsonl` | `evd_cards` + `evd_src_links` | `evidence_id` 映射 `evd_cards.code`；证据与一个或多个 passage 的关系由 `evd_src_links` 表达 | `quote_short` 只保留短摘；全文上下文不塞入 evidence card；`source_id` 只是兼容字段 |
| `data/evidence_clusters.jsonl` | `clusters` + `cluster_evd` | `cluster_id` 映射 `clusters.code`；`linked_evidence_ids` 经 evidence resolver 后进入 `cluster_evd` | cluster 不是新史料，不直接映射 score record |
| `data/thematic_anchors.jsonl` | `anchors` + 后续 `anchor_links` | 聚合 theme/person 锚点可进入 `anchors` 候选表 | anchor 只做裁量辅助，不直接入分 |
| `data/thematic_anchor_objects.jsonl`、`data/thematic_anchor_events.jsonl`、`data/thematic_anchor_mechanisms.jsonl` | `anchors`；语义稳定后再拆 `anchor_evd`、`anchor_cluster`、`anchor_person` | object/event/mechanism 锚点先收束为统一 anchor 层，用 `anchor_type` 区分 | 不在 PostgreSQL 中机械复制三张同构表；`item/subitem` 只做范围过滤 |
| `data/object_anchor_coverage.jsonl` | `anchor_links` 或后续 `anchor_evd/anchor_cluster/anchor_person`；待裁判项可进 `review_items` | converted evidence card 和 unresolved lead 需要最小锚点覆盖、`no_anchor_reason` 和审计链时进入关系层 | 不做自动评分表；不允许 person-specific override；未决 lead 仍不得入分 |
| `data/trigger_terms.jsonl` | staging-only，后续是否建 `terms` 另议 | 仅作为检索种子、trigger family 和 query 生成参考 | 不把关键词树扩回 `project_config.yml`；不作为生产 search task 状态 |
| `data/events.jsonl` | staging-only，后续是否建 event target 另议 | 只有当事件层成为跨项稳定对象时再设计目标表 | 当前不把 event row 当证据关系或评分关系 |

未来 PostgreSQL 第一版仍应以采集和证据链为边界，覆盖 `persons`、`person_aliases`、`subitems`、`src_hosts`、`src_docs`、`doc_revs`、`passages`、`passage_people`、`query_profiles`、`search_tasks`、`search_hits`、`cand_matches`、`evd_cards`、`evd_src_links`、`clusters`、`cluster_evd`、`review_items`、`imports`、`import_rows` 等。`adjudications`、`score_records`、`score_releases` 不属于本设计的当前实现范围。

#### Object-anchor home

对象锚点分两层保存：

1. 可复用锚点目录：稳定对象、事件、机制进入 `data/thematic_anchor_objects.jsonl`、`data/thematic_anchor_events.jsonl`、`data/thematic_anchor_mechanisms.jsonl`。这些行描述锚点本身，例如对象名、对象类型、对象层级、可用于何种裁量辅助、相邻项风险和审核状态。
2. 覆盖记录：每个 converted evidence card 和 unresolved lead 的最小锚点元数据进入 `data/object_anchor_coverage.jsonl`。覆盖记录引用 `search_id`、`evidence_id`、`cluster_id` 或 `anchor_id`；若没有可用锚点，必须写 `no_anchor_reason`。

`evidence_cards.jsonl` 和 `search_logs.jsonl` 可以保留轻量引用字段，例如 `anchor_ids`、`anchor_coverage_ids`、`no_anchor_reason`。不再把完整 `object_anchor_metadata` 在多张卡、多个 log 和多个 batch 文件里反复复制。

#### Query-lane coverage home

query lane coverage 不再长期嵌入每个 batch 的 `source_evidence_specs.jsonl`。长期位置分三层：

1. `data/query_profiles.jsonl` 定义应查方向和 coverage policy。
2. `data/search_logs.jsonl` 记录每条具体 lane lead 的回源、转卡、未决或排除状态。
3. `data/query_lane_coverage.jsonl` 汇总每个 batch/person/subitem 的 lane 覆盖，明确 positive、negative、adjacent 三类 lane 的覆盖、转卡、未决和排除理由。

最小 coverage 记录建议字段：

```json

  "query_profile_id": "QRY-I5B-LIUHENG-20260628",
  "person": "刘恒",
  "item": "第五项",
  "subitem": "第五项B",
  "lane_group": "negative",
  "lane_name": "任人唯亲 / 近幸偏私",
  "query_term_groups": [["邓通", "近幸", "偏私", "宠臣", "任人唯亲"]],
  "coverage_status": "pending_review",
  "search_ids": ["SRCH-I5B-LIUHENG-NEG-DENGTONG-001"],
  "linked_evidence_ids": [],
  "excluded_with_reason": "",
  "unresolved_reason": "待回源并切分财政特许、私恩和后续清算相邻项",
  "anchor_coverage_ids": ["ANCOV-I5B-LIUHENG-NEG-DENGTONG-001"]
}
```

允许的 `lane_group` 建议保持小集合：`positive`、`negative`、`adjacent`。允许的 `coverage_status` 建议保持小集合：`converted_to_card`、`pending_review`、`excluded_with_reason`、`not_applicable_with_reason`、`covered_by_canonical_refs`。

每个 batch 报告必须列出三类 lane：

- 正向 lane：覆盖了哪些识人、授权、容谏、人才通道、团队结构或长期网络方向。
- 负向 lane：覆盖了哪些任人唯亲、近幸偏私、权奸酷吏、表达安全、功臣安全或同一对象反转方向。
- 相邻项 lane：覆盖了哪些战功、制度后效、政权安全、刑罚残酷、思想控制等切分方向。

每条 lane 必须说明转卡、未决或排除理由。未决 lead 不能因为存在 lane 就被当作负证或正证。

#### Batch folder allowed contents

`data/batches/<batch_id>/` 只允许承载过渡期材料：

- `manifest.yml`：批次 ID、生命周期状态、scope、canonical merge policy、canonical row refs、保留理由。
- `source_evidence_specs.jsonl`：draft 或 active review 阶段的可重复生成输入；吸收到 canonical 后不再作为长期主输入扩张。
- `source_pack.jsonl` / `source_review_log.jsonl`：未吸收到 `data/source_packs.jsonl`、`data/search_logs.jsonl` 前的回源包和回源日志。
- `query_profiles.jsonl`、`search_logs.jsonl`、`sources*.jsonl`、`evidence_cards*.jsonl`：仅限未吸收或部分吸收的 staging rows。
- `review/*.jsonl`：人工审阅包、readiness audit、adjudication draft 等 review-only 材料。

batch folder 不允许承载 generated `exports/**`、评分规则、定档规则、person-specific override、长期关键词树、每人每子项每轮补丁式 micro supplement 目录，或已经完整吸收到 canonical 后仍作为 exporter/test 主输入的重复 JSONL。

#### 什么时候指向 canonical row IDs

批次文件在 `draft_batch` 或 `active_review_batch` 阶段可以暂时复制结构化 rows。一旦 stable ID 已进入 canonical，batch folder 应改为指向 canonical row IDs：

- `manifest.yml` 记录 `canonical_row_refs`，例如 `query_profile_ids`、`search_ids`、`source_ids`、`source_pack_ids`、`evidence_ids`、`cluster_ids`、`lane_coverage_ids`、`anchor_coverage_ids`。
- 批次内 JSONL 只保留 review-only snapshot 或 absorption audit；不得继续作为生成器的首选输入。
- 部分吸收时，manifest 必须分清 `absorbed_to_canonical`、`pending_canonical_absorption`、`review_only` 三类文件。

## 三、query_profile 与 search_log 的关系

1. 通用 `query_profile` 定义项目级检索框架。
2. 人物级 `query_profile` 定义某人物在本项目中应查的正向维度、负向维度和相邻项风险。
3. `search_log` 是由 query_profile 派生出的具体检索线索。
4. `search_log` 只保证覆盖入口，不保证每个入口都必须转证据卡。
5. 每个维度可以有多条史料证据，但是否建卡取决于回源质量、直接相关性、新维度价值和裁量必要性。
6. 每个证据批次必须报告正向、负向、相邻项 query lanes 的覆盖、转卡、未决和排除理由；报告位置可以是 PR body、批次 manifest、`source_review_log` 或明确的 review log，但不得只写在临时对话中。

禁止把人物级 query_profile 当成证据或结论。它只回答：“为什么要查这些方向？”不回答：“这个人应得什么档？”

## 四、证据卡、证据组与对象锚点的关系

1. 证据卡是原子证据，只记录已回源且能归项的材料。
2. 证据组不是新史料，而是对同向、多卡、可裁量材料的结构性合成。
3. 多条同类证据可以增强结构性，但不得按条数机械加分。
4. 同类证据达到代表性覆盖后，后续同类材料只增厚元数据，除非提供新维度、强反证、反转材料或相邻项切分价值。
5. 强正或强负证据组必须接受反向检索和相邻项切分复核。
6. 对象锚点只校准证据权重，不替代 source、evidence_card 或 evidence_cluster，也不直接进入定档。
7. 人才安全处置锚点等对象标签应嵌入证据卡/证据簇层，不应单独演化成多轴笛卡尔积计算。

## 五、清理与归档规则

阶段完成后，按以下顺序清理：

1. 确认批次文件内容已合并入 canonical 主表，或明确决定不合并。
2. 确认正式导出视图已经生成。
3. 删除无用临时草稿、调试导出、重复批次文件。
4. 对有审计价值但不再参与执行的批次文件，可移动到归档区或保留在 PR 历史中。
5. 不删除仍是唯一数据来源的批次文件。
6. 不保留会造成平行评分系统的对象池草稿；只保留已被规则引用或可复用的最小锚点。

删除或归档前必须确认是否唯一数据源。

若文件仍被测试、脚本、导出、README、治理文档引用，不得删除。

对 `archive_candidate` 和 `delete_candidate` 级别的高风险文件，必须单独开 PR，不得混入业务 PR。

第一轮只允许诊断，第二轮才允许小范围归档或删除。

导出视图可删除或归档的前提是能从事实源或批次源重建，或用户明确确认只保留 PR 历史。

## 六、最低追溯链

正式进入定档前，至少应能追溯以下链条：

```text
query_profile
→ search_log
→ source
→ evidence_card
→ evidence_cluster
→ 净证据池/裁量复核
→ 自动结算规则敏感点清单
→ 自动结算草案
→ 定档前人工裁判清单
→ 正式定档落地表
```

如果某一步暂时使用批次文件而非 canonical 主表，应在 PR 或审计视图中说明。

对象锚点若参与证据权重裁量，应能追溯到对应证据卡、证据组或专题锚点；不得脱离证据链单独决定档位。

未来史源上下文平台的最低追溯链扩展为：

```text
query_profile / search_task
→ source_document
→ source_passage
→ evidence_source_link
→ evidence_card
→ evidence_cluster
→ adjudication_decision
→ score_record
```

当前 JSONL 过渡期可暂用 `source_id` 连接 `sources.jsonl` 与 `evidence_cards.jsonl`，但不得把全文上下文塞入 evidence card 来替代 source passage。

## 七、执行口径

- 日常推进允许使用批次文件降低写入风险。
- 阶段收束时必须回到 canonical 主表与正式导出视图。
- 规则文档宁少勿散；数据文件宁结构化勿长篇散文。
- 对象锚点宁少勿全；先服务裁量，再考虑沉淀，不为每个项目预建全量对象库。
- 不展示阶段总榜、不定分、不排名，除非当前流程已经进入正式定档/汇总阶段并且用户明确要求。

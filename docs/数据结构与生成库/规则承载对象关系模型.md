# 规则承载对象关系模型

本文定义“某条规则到底由哪些对象承载”的中间结构。它解决 `obj_srcs.rule_id` 同时承担史源链接、规则相关性、计分承载和上下文说明时容易出现的错挂、重复计分和人工判断不透明问题。

本文只规定数据结构和工作流，不替代分项规则、证据簇公式或人工回源裁量。当前 I5B 正式算分仍以对象链、结构化因子表、`evd_cluster_calc_details` 和 `emp_item_result_calc_details` 为准；本模型作为重算后的硬审计影子层运行，用来确认规则承载对象和上下文关系，暂不直接替代 `calc_detail` 作为算分输入。

## 问题边界

当前链路里，`obj_srcs` 一条记录同时表示：

- 某对象有一条已回源史料；
- 该史料和某个 `item_id + rule_id` 有关；
- 该对象可能进入该 rule 的计分；
- 该对象也可能只是身份、属性、事件或机制上下文。

这对简单人物对象足够，但遇到规范化对象后会有副作用。例如同一事实链里同时有施害机制、受害群体和具体能臣，若三者都挂到 `tolerate_talent` 并直接进分，就会把同一因果链重复计分。又例如 `anti_nepotism` 需要承载具体受宠任用对象，机制型对象只能解释背景，不能代替武三思、张易之等人物成为计分承载对象。

因此需要把“史料对象存在”与“规则计分承载对象”拆开。

## 核心结构

### 事实关系

`fact_relations` 记录对象之间的事实关系：

- `subject_obj_id`：关系主体对象；
- `predicate`：关系谓词，例如 `favorite_beneficiary`、`harmed_by_enabled_actor`、`mechanism_context_for`；
- `object_obj_id`：关系宾语对象，可为空；
- `obj_src_id`：支撑该关系的对象史料；
- `causal_chain_key`：同一因果链的稳定键；
- `relation_role`：该关系在后续规则判断中的角色，例如 `scored_candidate`、`actor_context`、`mechanism_context`、`victim_context`。
- `source_method`：关系来源，例如人工确认、从 `obj_srcs` 候选生成、从计算明细候选生成或历史回填。
- `review_status`：审核状态。候选生成默认是 `needs_review`，人工确认后才可进入 `accepted`。
- `review_note` / `note`：默认留空，只写人工审核理由或无法由结构字段还原的补充事实；候选来源、待审状态、皇帝、rule、对象和 predicate 不写成模板备注。

事实关系回答“对象之间是什么关系”，不直接回答“该 rule 算谁”。人工查看需要的展示句由 `v_fact_relations_by_id.display_note` 或报告层动态生成，不在 `fact_relations.note` 中冗余存储。

`fact_relation_predicate_options` 是事实关系谓词词表，用来限制候选生成器可以从哪个 `rule_code + scoring_role` 生成哪个 `predicate + relation_role`。第一版 I5B 词表只对具体 `person` 生成候选关系；机制、事件和群体不直接进入 `fact_relations` 的计分候选，只能在人工确认后作为上下文成员或后续关系补充。

词表行的 `description` 承担人类可读语义说明；`note` 默认留空，只写单条词表项的特殊边界或迁移状态，不重复写“本表是 I5B 最小词表”这类全表说明。

硬通货事实采集可以先产出 `fact_relation_hints.jsonl`，作为尚未进入 `fact_relations` 的跨项候选。例如某将领受命统军并取得战役结果，既能支撑第五项B的任人信任或合理授权，也可能支撑后续国防安全类项目。hint 阶段只记录主体对象、史源、动作/结果摘要、`predicate_hint` 和潜在目标项；只有当目标 item/rule、谓词词表和承载对象都确认后，才可转换为 `fact_relations` 或 `rule_evidence_units` 候选。

当前 I5B 最小词表包括：

- `anti_nepotism`：`favored_kin`、`favored_private_person`、`interfered_appointment`、`resisted_nepotism`；
- `tolerate_talent`：`protected_talent`、`accepted_remonstrance_actor`、`harmed_talent`；
- 其余 I5B rule 也预置了 person 型基础谓词，供后续扩展审计使用。

因皇帝本人目前不是 `raw_objs` 中的对象，自动候选阶段通常以具体人物为 `subject_obj_id`，`emp_id` 限定皇帝语境，`object_obj_id` 暂空。若后续补建皇帝 raw object 或更精细主谓宾关系，再把 `object_obj_id` 或独立上下文关系补齐。

### 规则证据单元

`rule_evidence_units` 记录某个 `emp_id + item_id + rule_id` 下实际选择的计分承载单元：

- `causal_chain_key`：对应事实链；
- `scored_obj_id` / `scored_obj_src_id`：本单元实际计分的对象和材料；
- `scoring_role`：该对象为什么承载本 rule，例如 `favorite_beneficiary`、`harmed_talent`；
- `direction`：本单元方向；
- `score_mode`：`shadow` 表示只影子预览，`scoring` 表示未来接入正式计算，`rejected` 表示已审掉。
- `source_method` / `review_status`：区分机器候选、人工确认和人工驳回。`review_status != accepted` 的单元不得作为正式算分输入。
- `review_note` / `note`：默认留空，只记录人工审核理由或无法由结构字段还原的补充事实；候选对象名、角色和 rule 不写成模板备注。

`rule_evidence_unit_members` 记录同一单元内的上下文成员，例如施害者、机制、事件、群体、补源材料。成员可以解释和支撑计分对象，但不等于自己入分。成员表的 `review_note` / `note` 同样默认留空；人工查看所需的承载对象句和成员句由 `v_rule_evidence_units_by_id.display_note`、`v_rule_evidence_unit_members_by_id.display_note` 或报告层动态生成。

## I5B 规则承载口径

### `anti_nepotism`

计分承载对象必须是具体受宠、受亲缘偏私或干预任用的人：

- `nepotistic_beneficiary`：亲族、外戚等亲缘偏私受益者；
- `favorite_beneficiary`：宠幸、近幸、面首等私人偏好受益者；
- `appointment_interferer`：实际干预任用秩序的人。

机制、事件、制度氛围和笼统群体只能作为成员解释。若对象属性或史料只说明“存在酷吏罗织机制”，它可以成为 `mechanism_context`，但不能直接替代具体偏私对象进入 `anti_nepotism` 计分。错误任用酷吏若只能证明“委政制狱”或“受任推狱”，应优先归入 `appointment_trust`、`delegation` 或 `tolerate_talent`，不得仅凭酷吏身份进入 `anti_nepotism`。

### `tolerate_talent`

计分承载对象必须具体到被保护或被伤害的人：

- `protected_talent`：被保全、复用或修复信用的能臣；
- `remonstrance_actor`：被容纳的进谏者或表达者；
- `harmed_talent`：被压制、冤杀或排挤的能臣；

施害者、酷吏机制、诬陷事件和被害群体通常是成员，不直接计分。若同一因果链同时出现事件对象、受害群体对象和具体被害人物，应优先选择具体人物作为计分承载对象，其余对象作为成员，避免重复计分。

### 其他 I5B rule

- `talent_discovery`：计分承载对象是被发现、提拔、推荐或识别的人才；荐举机制和考试制度通常是上下文。
- `appointment_trust`：计分承载对象是被任用、信任、误任或被政治性压制的人；诏令和制度安排通常是上下文。
- `delegation`：计分承载对象是被授予、被撤回或被错误授予权力的具体对象；授权制度或战时背景通常是上下文。
- `team_building`：当前仍以 `emp_objs + obj_attrs.talent_quality` 自动取团队候选；关系单元只用于解释候选为什么归入团队，不替代人才质量属性。

## 跨大项适用示例

这套机制不是 I5B 专用。它适合所有“对象存在”和“规则承载”容易混淆的场景。

- 军事项：战役对象、将领对象、后勤机制和边疆局势可以同属一条因果链；计分承载可能是战役结果，也可能是统帅任用，不应让战役和将领重复扣同一事实。
- 财政项：税制、具体财政官员、灾荒背景和民变可以连成关系链；计分承载应区分制度收益、执行者能力和社会后果。
- 司法项：酷吏、冤案、司法制度和被害群体可以同时入库；计分承载应选择冤案或被害对象，酷吏多为施害者上下文。
- 文治制度项：科举、学校、典籍整理和具体文臣可以互相支撑；制度对象与人物对象的贡献应按规则槽位拆开。
- 亡国型负向：亡国事件、关键失策者、财政崩塌、军队溃散和外敌压力通常同链；各 rule 只取本 rule 的承载对象，其他对象作为上下文成员。

## 影子运行流程

第一阶段只影子运行：

```text
src_docs / raw_objs / emp_objs / obj_srcs / obj_attrs
-> candidate payload（source_method=candidate_from_calc_detail，review_status=needs_review）
-> preview / audit
-> rule_evidence_units / rule_evidence_unit_members（候选写入，等待人工确认）
-> fact_relation_predicate_options（限定 rule/scoring_role 到 predicate 的候选映射）
-> fact_relations（只生成词表允许的具体 person 候选关系，等待人工确认）
-> 人工确认是否调整 obj_srcs 或 calc_detail
```

在这一阶段，正式证据簇仍从当前明细表重放；`rule_evidence_units` 只帮助判断对象关联是否合理。

第二阶段可把 `rule_evidence_unit_id` 写入 `evd_cluster_calc_details.calc_detail.materials[*]`，用于解释每条计分材料来自哪个规则证据单元。

第三阶段若影子层稳定，再考虑让证据簇计算直接读取 `rule_evidence_units`。只有到这一阶段，`obj_srcs.rule_id` 才能退回“规则相关史料边”，不再独自承担计分承载判断。

## 审计原则

- 一个对象可以在多个 rule 下有关系，但每个 rule 必须说明它在该 rule 中的 `scoring_role`。
- 同一 `causal_chain_key` 下的机制、事件、群体和人物不得无解释地同时计分。
- 机制和事件默认是上下文；只有规则明确允许，且没有更合适承载对象时，才可成为计分对象。
- `raw_objs.note` 继续只写身份和事实；承载角色写入关系层或规则证据单元，不回填到原始对象 note。
- `obj_srcs.note` 继续写史料事实对规则维度的帮助；是否入分由规则证据单元或计算明细解释。
- 自动候选不得绕过审核。候选生成器可以从 `obj_srcs`、`obj_attrs` 和 `evd_cluster_calc_details` 还原当前计分承载，但不能把 `raw_objs.note` 或史料全文自由文本直接当作已确认事实关系。

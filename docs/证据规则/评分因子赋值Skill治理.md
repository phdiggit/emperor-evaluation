# 评分因子赋值 Skill 治理

本文档规定评分消费链中何时允许引入 Codex skill 辅助因子赋值。Skill 只用于降低系统性赋值漂移，不替代评分标准、分项规则、规则表、证据裁量或最终定分。

## 基本定位

- Skill 是因子赋值辅助规程，不是业务事实源。
- Skill 只服务首次消费或重跑消费时的判断质量，不用于单人 override。
- Scorer、正式公式和规则细则表不得从 skill 读取业务语义。
- 旧库、旧账本和旧定分只可作为参考材料或回归样本，不可因 skill 存在而重新联动旧结果。

## 三档治理

| 因子赋值状态 | 处理方式 | 说明 |
| --- | --- | --- |
| 基本稳定 | 不建 skill，正常消费 | 结构校验、枚举校验和常规诊断已足够。 |
| 小比例边界问题 | 诊断、抽样或 worklist 复核 | 不为少量边界个案增加常驻上下文成本。 |
| 不小比例系统性偏差 | 建窄 skill，并重跑相关消费 | 只覆盖出现系统偏差的因子或小因子组合。 |

系统性偏差包括：同一因子在多目标、多对象或多批次中反复出现同方向高估/低估；模型容易被官职、战功、名气、后果严重性或相邻项语义带偏；结构校验能通过但人工抽查显示赋值口径不稳。

## 建 Skill 原则

1. 只对误差明显的因子或小因子组合建 skill，不为整条流程、整张表、整项评分或每个皇帝建 skill。
2. Skill 名称必须体现适用范围，例如 item、rule 和关键 factor。
3. `SKILL.md` 只放高风险边界、自检顺序和少量校准例，不复述评分总则和数据库流程。
4. 详细例子如确有必要，放入 references，并要求仅在边界材料不确定时读取。
5. 每个 skill 必须能回答“它解决哪类系统性赋值偏差”，否则不应创建。

## 版本与追踪

消费产物应尽量记录使用过的 `skill_name`、`skill_version`、`skill_hash`、`prompt_hash` 和 agent/task 标识。当前阶段可先写入本地 run artifact 或 judgment payload；当 skill 数量和版本回放需求增长后，再新增轻量 guidance version 表，只存版本元数据和 hash，不把 skill 正文塞入业务 judgment 表。

## 当前试点

首个试点为 `i5b-delegation-factorization`，仅服务第五项B `delegation` 的 `authorization_intensity` 与 `result_feedback`。这两个因子已显示出不小比例系统性偏差：容易把高官、大战、普通胜利或严重后果直接推成高档；也容易把相邻 rule 材料误当 delegation 结果反馈。试点目标是让首次因子化消费就按稳定标尺赋值，而不是依赖事后补丁。

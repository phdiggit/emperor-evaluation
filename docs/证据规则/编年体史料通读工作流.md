# 编年体史料通读工作流

> 状态：`accepted`
> 适用范围：唐以后正史本纪、编年体及其他按卷连续阅读的固定修订史料
> 唯一入口：本文件同时定义四域同读、战役登记、并发调度、运行环境、逐卷验收和恢复规则；不再另设战役通读草案。

## 一、目标与不可妥协边界

每个固定修订区段只完整读取一次。通读时先形成中性共享事实，再自然路由到：

- `battle`：战役与战争行动；
- `fiscal_livelihood`：财政、生产流通、赋役、灾荒、赈济和社会状态；
- `public_works`：工程决策、投入、施工、运行、受益与损害；
- `political_event`：关键选择、权力变化、纠错止损及其直接结果。

本流程交付可回读、可续接、可确定性重建的事实和候选，不直接产生皇帝归责、成果档位、规则方向、分数、排名或生产数据库写入。政书仍按朝代扫描一次，用于补制度基线和跨期运行，不替代编年事件中的实际实施、责任和结果。

以下规则不可放宽：

1. 固定史源身份、修订和指纹先于阅读；卷界以固定索引中的完整卷页或显式下一卷号为准，不得把页内年号、帝号或章节标题误作卷界。
2. `unknown` 保持 `unknown`；不得为凑齐人物、数量、因果、域或结果而推断。
3. 每条引文必须逐字命中固定正文，至少包含 5 个汉字，并在本卷正文中唯一；长度按汉字计数，不按字符串字符数计数。
4. 每卷只允许一个 canonical 事实文件；阅读视图和路由登记由它确定性生成，不得手工维护第二套事实。验收后的可审计产物发布到 `docs/共享史料/<史书>/**`。
5. 已验收卷不重读。恢复只从首个未验收卷继续，并只读前一卷必要边界上下文。
6. 默认工作环境是用户指定项目的 Git 根目录，临时产物统一写入该项目的 `tmp/**`。未经用户明确允许，不得把工作环境迁入 `C:\Users\<user>\.codex\worktrees\**` 或其他会话 worktree。

## 二、旧流程为何慢

“先快速通读、最后集中返工”会把单卷问题积累成批量恢复：

- 未经允许把工作环境迁入会话 worktree，导致其中未追踪 `tmp/**` 随任务归档而消失；
- 三路使用不同根目录和局部约定，收口时才统一 Schema、ID、状态枚举和目录；
- 页内年号被误识别为下一卷，造成整段漏读；
- 引文只检查非空或原始长度，未检查汉字数、逐字命中和卷内唯一；
- 事实、路由登记和 Markdown 分别修改，产生多套不一致状态；
- 低密度、近似一事一引、终端截断等异常拖到五卷或全书终审才发现；
- 会话承载过多卷次和历史消息，后段发生合同漂移、遗漏和预算耗尽。

正确优化不是减少验收，而是把验收前移，使每卷只做一次完整阅读、一次 canonical 构建、一次相邻边界检查；只有异常卷和五卷边界使用更强模型。

## 三、项目内运行环境

### 3.1 目录布局

默认直接在项目的实际 Git 根目录运行。运行暂存集中到项目 `tmp/chronicle/**`，通过验收的可审计通读产物发布到项目 `docs/共享史料/**`：

```text
<project-git-root>\
├─ config\
├─ docs\
│  └─ 共享史料\
│     └─ <史书>\                 # 已验收、进入 Git 的可审计通读产物
├─ src\
└─ tmp\chronicle\
   ├─ source\                     # 当前任务固定史源缓存，只读
   ├─ accepted-staging\           # 发布前隔离双跑，不是最终事实源
   ├─ runtime\
   │  ├─ lane-1\                 # 可删除的分路暂存和日志
   │  ├─ lane-2\
   │  └─ lane-3\
   └─ audit\                      # 五卷和全局审计结果
```

每部史书的 `docs/共享史料/<史书>/` 至少保留：

- 每卷唯一事实 JSON；
- 由事实 JSON 自动生成的 registry JSON 和 Markdown；
- `manifest.json`：记录每卷状态、输入指纹、产物 hash、事件数、引文数和验收时间；
- 当前开放 thread 快照和下一卷待确认问题。

固定 `source.sqlite3` 或等价全文缓存保留在 `tmp/chronicle/source/**`，不提交 Git；可审计产物通过逐卷验收后才进入 `docs/共享史料/**`。项目 `tmp/**` 不进入 Git，成功收口后按项目清理规则删除。若用户明确批准迁移，必须先验证 manifest、文件数和 hash，再删除旧副本。

### 3.2 环境变量与执行器

PowerShell 7 会话先从 Git 解析项目根，再使用项目内路径：

```powershell
$projectRoot = (git rev-parse --show-toplevel).Trim()
$env:PYTHONUTF8 = '1'
$env:CHRONICLE_CONTRACT_REPO_ROOT = $projectRoot
$env:CHRONICLE_OUTPUT_ROOT = Join-Path $projectRoot 'tmp\chronicle'
$env:CHRONICLE_AUDITABLE_ROOT = Join-Path $projectRoot 'docs\共享史料'
codex-win run -- python <current-validator> --input <registry.json>
```

- `CHRONICLE_CONTRACT_REPO_ROOT` 必须是当前项目 Git 根，提供代码、Schema 和确定性构建器；
- `CHRONICLE_OUTPUT_ROOT` 固定为当前项目的 `tmp/chronicle`，只承载运行暂存；
- `CHRONICLE_AUDITABLE_ROOT` 固定为当前项目的 `docs/共享史料`，只接收已验收产物；
- 中文、多行 JSON 或 Markdown 不通过 PowerShell inline 传递，使用 UTF-8 文件；
- 每次启动先做 preflight：`git rev-parse --show-toplevel` 与用户指定项目一致、当前根不是会话 worktree（除非用户明确允许）、`tmp/chronicle` 可写、固定缓存可读、剩余空间满足整批要求、合同 hash 一致；任一失败不得开始读卷。

### 3.3 原子发布

每路只能写项目内自己的 `tmp/chronicle/runtime/lane-*` 暂存，并只发布 owner map 授权卷号对应的 `docs/共享史料/<史书>/**` 文件。单卷通过全部验收后，由确定性发布器把该卷产物原子发布到共享史料目录；共享 README、总索引和 manifest 只能由主控在五卷边界或终审时重建。任何时候都不允许：

- 两路同时写同一卷；
- 直接在 `docs/共享史料/**` 文件上边生成边调试；
- 以会话聊天记录、终端输出或自由文本总结代替 checkpoint；
- 只看命令退出码，不读回状态和产物。

## 四、最优并发拓扑

### 4.1 一个主控、三条读卷路

在四个可用任务槽下，采用“一个轻量主控 + 三条读卷路”：

- 主控只负责任务范围、owner map、验收结果、异常升级、会话轮换和最终审计，不亲自持续读卷；
- 三条读卷路分别拥有连续且不重叠的卷段；
- 每卷只有一个写入者；分路边界各自额外只读相邻一卷的边界摘要，不复制其事实；
- 同一史书足够长时按连续三段并发；史书不足三段时，把空闲路分配给另一部未完成史书；
- 不为单卷再启动内部子 Agent。嵌套并发会增加上下文、写入冲突和验收成本。

读卷路数量为 `min(3, 可用任务槽 - 1, 可安全分割的连续卷段数)`。三路并发追求稳定吞吐，不追求理论三倍；主控、五卷审计和边界合并会产生必要开销。

### 4.2 owner map

启动前写入唯一 `owner-map.json`：

| 字段 | 含义 |
| --- | --- |
| `task_code` | 稳定任务代码，不随会话轮换改变 |
| `source_identity` | 史书、固定 revision、缓存 fingerprint |
| `lane_id` | 唯一读卷路 |
| `owned_range` | 允许发布的连续卷段 |
| `boundary_context` | 只读相邻卷号 |
| `canonical_root` | 项目 Git 根下唯一 `docs/共享史料/<史书>` 路径 |
| `next_volume` | 首个未验收卷 |
| `contract_hash` | 本工作流、Schema 和构建器组合指纹 |

主控不得仅依据聊天中的“当前卷号”调度；manifest 和 owner map 才是状态事实源。史书完成后先终审并关闭 task，再把空闲路分配给下一未完成范围；不得跨史书复用未清空的开放 thread。

### 4.3 分段原则

优先按卷数与正文净字数共同均衡，避免只按卷号三等分。已知特别密集的战争、改朝换代或长卷，应减小该路卷数。分路边界尽量落在五卷审计点；不得为了均衡把一卷拆给两路。

## 五、会话与模型设置

| 任务 | 模型 | reasoning | 单次会话范围 | 说明 |
| --- | --- | --- | --- | --- |
| 普通卷完整阅读与事实草拟 | `gpt-5.6-terra` | `medium` | 正常 5—8 卷，密集 4—6 卷 | 主力路径，严格按固定合同输出 |
| 低密度、截断、近 1:1、拆合争议、错源修复 | `gpt-5.6-sol` | `medium` | 只处理异常卷或异常批 | 不扩大到已通过卷 |
| 每五卷累计审计 | `gpt-5.6-sol` | `medium` | 固定五卷 | 覆盖、重复、边界和幂等 |
| 分路边界与全书终审 | `gpt-5.6-sol` | `medium` | 只读结构化产物和必要原文 | 不重新通读全书 |

会话按 5 卷审计单元设计：通常在 5—8 卷后主动轮换，最多不得超过 10 卷；密集材料最多 6 卷。新会话只携带：

1. 本工作流和 Schema 的 hash；
2. 固定史源 identity/revision/fingerprint；
3. owner map 中本路范围和唯一持久路径；
4. 最近 1—2 卷的边界摘要、开放 thread 和下一卷问题；
5. manifest 中的 `next_volume`。

不得携带整段旧对话、全批自由文本总结或中间失败版本。模型切换不改变 task code、owner、路径或事实 ID。

## 六、共享事实与四域路由

### 6.1 `chronicle_fact`

共享事实是可逐字回读的一次行动、实施、状态变化或直接结果。至少保存：

- 最窄可知时间、地点和行动主体；
- 行动、实施、可观察结果、代价或负担；
- 受影响群体；
- 史料原称、已解析人物/政权及实际动作；
- `semantic_fingerprint`；
- 精确 `page@revision#quote`；
- 各域路由、理由和不确定性。

事实拆合使用“同日、同主体、同目标、同一连续因果链”。四项同时成立才合并；任一变化且能形成独立行动或结果时拆分。标题相同、地点相同或后世归入同一大事，不能单独决定合并。纯任命、纯礼仪和无行动结果的名单不单独成卡；任命若直接改变军政权力、危机处置或实施结果，可并入对应事实链。

### 6.2 路由结果

| 域 | 路由 | 当前阶段保存 | 后置阶段判断 |
| --- | --- | --- | --- |
| `battle` | `HANDOFF_BATTLE_WORKFLOW` | 战争事实、双方动作/结果、campaign thread | 战役档位、难度、人物消费、分数 |
| `fiscal_livelihood` | thread 操作、`BELOW_THRESHOLD`、`CONTEXT_ONLY` | 基线、财政、民生、生产流通 | C1/C2/D2 等规则结算 |
| `public_works` | thread 操作、`BELOW_THRESHOLD`、`CONTEXT_ONLY` | 工程阶段、投入、运行、受益、损害 | 各评分项消费 |
| `political_event` | thread 操作、`BELOW_THRESHOLD`、`CONTEXT_ONLY` | 问题、备选、选择、权力变化、直接结果 | 关键决策、政治风险等判断 |

同一事实可以多域路由，但同一域最多一个 route；多域复用同一 `fact_id` 和史源，不复制事实正文。非战役 thread 操作统一为 `OPEN_NEW_THREAD / APPEND_EXISTING_THREAD / SPLIT_THREAD / MERGE_THREADS / CLOSE_CANDIDATE`。战役使用专门的 `campaign_thread`，不得塞入通用 thread。

财政增加不自动等于民生改善；下诏修建不等于完工，完工不等于有效运行；政治事件不因“皇帝在位”自动归责皇帝。史料未载的观察项保留“未载”和 uncertainty。

### 6.3 三类非战役候选的最低观察项

- 财政民生：`baseline`、`fiscal_state`、`livelihood_state`、`production_circulation`；战争缴获不能直接等同财政健康，国库增加不能直接等同民生改善。
- 大型工程：`work_identity`、决策/征发/建设/完工/运行/维修/废弃阶段、原载目的、`resource_input`、实际运行、`benefit` 和 `harm`；宫殿、陵墓、边墙、运河、水利和道路使用同一生命周期。
- 政治事件：`event_type`、`decision_question`、史料明确记载的 `alternatives`、实际 `decision`、`direct_result`、`power_change`、已暴露的 `risk_or_damage` 和 `follow_up`；未实施建议、纯言论和史家评论只作背景。

候选必须完整消费 closed thread 的事实，不得只挑有利片段。它仍是中性登记输入，是否晋升成果、风险或评分证据由后置合同判断。

## 七、战役通读与登记

本节完整取代原战役通读草案。

### 7.1 对象

- `chronicle_war_fact`：出兵、会师、交战、围城、解围、追击、投降、撤军、议和、换帅、断粮、主力覆灭等最小可核验事实；
- `campaign_thread`：跨页、跨卷续接的目标、参战方、战区、指挥链、阶段结果和未决问题；
- `closed_campaign_candidate`：目标和边界已闭合、可交后续裁决的中性候选；
- `identity_resolution`：按有效时间解析姓名、爵号、官号、旧名、政权别称和阵营变化；无法确认时保持未知。

### 7.2 双边和多方事实

一场战事只建立一组中性事实，但对每个参战方分别记录：

- 当时的 `side_ref`、`polity_ref` 和目标；
- 决策、统筹、临阵指挥、独立方面和关键执行等实际动作；
- 胜利、失败、部分达成、胜而未克、撤退或未决；
- 稳定控制变化、敌我主力影响和自身损失；
- 换帅、违令、误判、救援不力、擅退等负面事实。

名义主帅、官职、皇帝授权和参战名单只解释权责，不自动生成能力成果。先敌后友、降附或叛变按时间切分阵营，不把后来的身份反写到此前事实。

### 7.3 campaign 路由

战役事实只能执行：`OPEN_NEW_THREAD / APPEND_EXISTING_THREAD / SPLIT_THREAD / MERGE_THREADS / CLOSE_CAMPAIGN / REDIRECT_NON_BATTLE / BELOW_THRESHOLD`。

是否续接主要看战略目标、参战主体、动员、战区、指挥链和直接因果是否连续。卷末、年末、换帝、换年号或史书改称都不是自然闭合点。

目标完成或明确失败、一方撤军/议和/投降、目标区统治结构终结，且没有立即延续同一目标的行动时，才可闭合。短暂停战、季节撤军或同一动员下换帅不得强行闭合；后续多年新动员和新目标也不得反向吞并已闭合战役。

跨多年、多战区、目标或指挥体系改变时优先拆分；同一目标下被卷次机械切开、追击围歼受降只是决战完成环节时优先合并。拆分后的子战役可挂同一上位战争，但不得把上位战争全部体量复制给每个子战役。

宫廷政变、刺杀、劫狱、无成建制作战的局部兵变转交 `political_event`。小规模骚扰、普通驻防或已被另一候选完整包含的环节可以 `BELOW_THRESHOLD`，但必须保留事实、理由和来源，避免以后重扫。

以下情形必须由 Sol 做语义复核，不能快速闭合：跨卷、跨战区或多方参战；先败后胜、胜而未克或结果混合；多名统帅先后接任；名义主帅与实际贡献不一致；对手强度、稳定控制、主力毁伤或问题难度存在关键争议；候选可能显著改变高档战役或人才边界。边界完整、身份明确、双方结果清楚且无争功争议的低档自足战事，可以快速形成候选，但仍不在通读阶段定档。

### 7.4 战役候选交接

闭合候选必须完整消费 thread 的事实，并携带父群边界、各方目标与结果、土地/主力/统治结构变化、问题难度事实、各人物实际贡献和负面责任、尚存争议及全部原子事实引用。

通读阶段不得填写 S/A/D 档、完整消费系数、皇帝归责或成本收益结算。统一战争、开国兼并与一般边防安全的正式路由由战役底账后置裁决，不能在编年事实层机械传播 campaign 标签或重复结算。

## 八、单卷唯一执行流程

### 8.1 锁定完整正文

从固定缓存直接查询该卷的索引行和完整正文，记录史书、卷号、revision、fingerprint、净汉字数、首尾定位和相邻卷标识。必须读到固定索引确认的末尾；不得从页面标题或年号猜测范围。

### 8.2 一次线性通读

按原文顺序读完全文，边读边形成事实链、身份解析、四域路由和开放问题，不在整卷结束后凭记忆回写。阅读阶段可维护项目 `tmp/**` 草稿，但不得提前发布到 `docs/共享史料/**`。

### 8.3 构建前预检

构建器运行前必须达到零失败：

- 必填字段、枚举、时间和 ID 合同正确；
- 每条事实至少一个域路由，同一事实每域唯一；
- 所有引文逐字命中、汉字数不少于 5、卷内唯一，同卷不重复使用同一锚点；
- thread 成员、route 和候选双向一致；
- closed candidate 完整消费其 thread；
- Markdown 尚未手工产生或修改；
- 结尾事实与固定正文末段对应，没有终端截断。

### 8.4 异常检测

预检同时比较本卷净字数与相邻卷：

- 正文字数较多但事件显著偏少，或连续两卷密度异常低；
- 事件数与引文数接近 1:1，疑似一句一卡；
- 事件或引文数突然翻倍，疑似过度拆卡；
- 大量泛化锚、短锚或跨卷重复锚；
- 首尾不完整、卷界异常或 source identity 改变。

任一命中时暂停发布，升级 `gpt-5.6-sol medium` 做该卷覆盖或结构复核。确认遗漏不超过 5 项时定点修复；超过 10 项、错源、错卷界或整体拆合错误时整卷重构。6—10 项由 Sol 判断定点修复能否保持结构一致，否则重构。不得为赶进度放行异常卷。

### 8.5 一次 canonical 构建与发布

零失败后只运行一次正式构建：

1. 生成唯一事实 JSON；
2. 由事实 JSON 确定性生成 registry JSON；
3. 由事实 JSON 确定性生成 Markdown；
4. 运行 Schema、ID、UTF-8、史源和路由校验；
5. 在隔离暂存目录以相同输入再运行一次，比较全部产物 hash；
6. 审计上一卷/本卷的时间、事实链、开放 thread、重复事实和引文边界；
7. 全部通过后原子发布到 `docs/共享史料/<史书>/**`；主控按边界重建 manifest 和索引。

“一次构建”指一次 canonical 发布，不允许靠反复覆盖 `docs/共享史料/**` 调试。预检失败和隔离双跑均不得写共享史料目录。

## 九、五卷边界审计

每完成连续五卷，主控暂停该路续派，由 `gpt-5.6-sol medium` 对这五卷检查：

1. source identity、revision、fingerprint 和首尾覆盖；
2. 分段覆盖和低密度漏段；
3. 事实拆合、近 1:1 拆卡和异常骤增；
4. 四域自然分布、unknown 保留和纯任命排除；
5. 引文逐字、汉字数、卷内唯一和跨卷泛化重复；
6. thread lineage、候选完整消费和相邻卷边界；
7. Schema、全局 ID、UTF-8、registry/MD 一致；
8. 五卷全量双跑幂等。

审计确认的旧卷漏项必须在本批直接回修，不能留作“终审未决”。修复后重跑本批审计；通过才续派下一卷。

## 十、恢复、轮换与故障处理

### 10.1 恢复

恢复以持久 manifest 为准：验证 contract hash 和 source fingerprint，找到本路首个非 `accepted` 卷，清理其未发布暂存，读取前一卷边界摘要和开放 thread，然后继续。固定修订改变时建立新输入版本并明确失效范围；会话归档、模型切换或预算耗尽不触发重读。

### 10.2 会话轮换

主控在 5—8 卷主动轮换，最迟第 10 卷硬停止。旧会话完成当前卷验收和 checkpoint 后退出；新会话用同一 task code、lane、owner range 和持久路径接续。不得跨史书携带旧开放 thread，也不得让新旧会话同时拥有写权。

### 10.3 故障优先级

1. 错源、错 revision、错卷界：立即停止该路，整卷重构；
2. 项目 `tmp/chronicle` 不可用或项目所在磁盘空间不足：全部路停止发布，不迁移到会话 worktree；
3. Schema/ID/引文失败：只修当前未验收卷或当前五卷批；
4. 模型超时：保留已验收卷，新会话只续未验收卷；
5. 主控心跳失效：读卷路完成当前卷后停在验收边界，不自行扩展范围。

## 十一、全书与跨路终审

所有 owned range 完成后，主控执行一次结构终审，不重新通读：

- 每条分路边界执行前卷/后卷事实链和 thread 审计；
- 全书卷号连续、source identity 唯一、manifest 与文件集合一致；
- 全局事实、thread、candidate ID 唯一；
- 语义指纹和引文重复可解释，无跨路重复事实；
- 四域 route、战役交接、候选和开放 thread 状态闭合；
- registry/MD 均可由事实 JSON 零差异重建；
- 全书确定性双跑产生零差异；
- 汇总精确卷次、事实数、引文数、失败数和未决项。

终审通过后才可删除 `tmp/chronicle/runtime/**` 和发布暂存。canonical 事实、registry、Markdown、manifest、索引和终审摘要保留在 `docs/共享史料/<史书>/**` 并进入 Git；固定正文缓存和过程日志仍按项目 `tmp/**` 清理规则删除。正常流程不存在“从会话事件流恢复产物”或“跨工作树汇总”阶段。

## 十二、性能控制

效率来自减少重复工作：

- 固定正文每卷只完整读取一次；
- 普通卷使用 Terra，Sol 只处理异常、五卷边界和终审；
- 单卷验收后立即发布，不积压到整批；
- 只在相邻卷和五卷窗口内做高频审计，不在每卷后扫描全书；
- 三路按净字数均衡并发，不争写同一目录；
- 模型上下文保持 5—8 卷，避免长会话漂移；
- manifest 直接提供续读点，主控不反复读取完整任务历史。

运行报告记录每卷读取、预检、构建、审计和返工耗时，用于调整分段和异常阈值；时间指标只进入项目 `tmp/chronicle/runtime` 或 `audit`，不写入业务事实。不得设置以牺牲完整性为代价的固定“三分钟一卷”目标。核心效率指标是：已验收卷重读数为 0、canonical 恢复时间为 0、终审结构性返工卷数为 0。

## 十三、禁止做法

- 未经用户允许把工作环境迁入 Codex 会话 worktree；
- 把临时产物写到项目 `tmp/**` 之外，或让三路使用三个不同项目根后再搬运合并；
- 从页面标题、年号或终端截断输出猜卷界；
- 让普通卷都使用最高模型，或让每路内部再起子 Agent；
- 先生成自由文本总结，最后再重建事实、路由和战役；
- 只校验 JSON 可解析，不校验引文逐字和卷内唯一；
- 手改 registry 或 Markdown 来让校验通过；
- 以事件数多、四域齐全或高档战役多作为质量指标；
- 因单条身份不明而阻断整卷，或为通过合同强填未知；
- 在终审才首次检查低密度、拆卡、漏段和分路边界。

## 十四、启动任务模板

每条读卷任务必须明确写入：

```text
task_code: <stable-code>
contract: <absolute-path>/docs/证据规则/编年体史料通读工作流.md
contract_hash: <sha256>
schema: <project_root>\config\<current-chronicle-schema>.json
source_identity: <work>@<revision>#<fingerprint>
project_root: <git rev-parse --show-toplevel>
source_cache: <project_root>\tmp\chronicle\source\<work>\source.sqlite3
canonical_root: <project_root>\docs\共享史料\<work>
lane_runtime: <project_root>\tmp\chronicle\runtime\lane-N
owned_range: <start>-<end>
boundary_context: <previous>,<next>
next_volume: <volume>
model: gpt-5.6-terra
reasoning: medium
session_limit: 5-8 volumes; hard stop 10
write_scope: lane_runtime and owned docs/共享史料/<work> volumes only
forbidden: tracked files, scores, database, nested agents, other lanes
```

主控验收回执至少包含卷号、source identity、净字数、事实数、引文数、四域计数、预检失败数、相邻边界结果、幂等结果、产物 hash 和下一卷号。没有这些证据，不得只凭“完成”或退出码续派。

## 十五、接受条件

一次通读任务只有同时满足以下条件才完成：

- 全部目标卷各自恰有一份 accepted canonical 事实 JSON；
- 固定缓存和每卷 revision/fingerprint 可回读；
- 引文逐字、汉字数、卷内唯一和 ID 检查为零失败；
- registry、Markdown 与事实 JSON 零差异；
- 四域路由、战役双边事实、thread 和候选满足本合同；
- 分路边界、五卷审计和全书双跑幂等全部通过；
- accepted 卷未因会话轮换、归档、迁移或收口而重读；
- 过程产物全部位于项目 Git 根的 `tmp/chronicle/**`；已验收可审计产物全部位于 `docs/共享史料/<史书>/**`，未经许可没有会话 worktree 副本；
- 精确报告已读范围、事实数、引文数、失败、修复和未决项。

每次任务必须在启动模板中绑定当前有效的机器 Schema 和只读 validator；两者不存在、路径不在本项目 Git 根或 hash 未冻结时，不得开始正式通读。验证和通读均保持 report-only、offline-first、零评分写入、零排名写入和零数据库写入。

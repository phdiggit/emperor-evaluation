# 史料检索总则与项目-人物双轴工作流（讨论版 v0.2）

## 一、定位

本总则用于规范“如何查史料、如何记录线索、如何避免漏证和偏证”。

它解决的是裁量体系之前的问题：

> 原始材料从哪里来，怎样检索，怎样记录，怎样决定哪些材料进入证据卡。

它不直接定档、不直接定分，也不替代《证据裁量总则》。二者关系为：

```text
史料检索体系负责发现与回源；
证据裁量体系负责归项、切分、对象锚点校准和入分前处理。
```

推荐全流程为：

```text
检索计划
→ 线索发现
→ 回源核验
→ 原子证据卡
→ 五轴裁量
→ 触发式裁判模块
→ 证据组裁量结论
→ 净证据池
→ 自动结算规则敏感点清单
→ 自动结算草案
→ 定档前人工裁判清单
→ 正式定档落地表
→ 标尺定档定分
```

本工作流只管“材料如何进入证据链”。从检索线索、source host、source document、source passage、上下文窗口到 evidence source link 的链条必须可追溯；证据强度、五轴、对象锚点和人工裁判门槛进入《证据裁量总则》。

离线采集边界：

```text
联网抓取 / 页面缓存 / 采集层摘录
→ offline source pack
→ source pack 审计
→ 摘录候选与对象 payload
→ 回源裁量与对象链
```

联网抓取是采集层动作，不是评分工作流动作。offline source pack 是 workflow-agnostic 的采集层产物；I5B 只是当前默认 adapter / consumer。I5B 等子项主链应消费已经落盘、可复核、可重复读取的 source pack；运行主链时不得依赖现场网络状态、Wikisource 限流或缓存命中运气。

## 二、检索目标

史料检索体系应同时满足四个目标：

1. **召回率**：尽量避免漏掉关键正证、负证、反转材料。
2. **精确度**：避免把无关材料、总体光环、相邻项材料误入当前子项。
3. **抗偏性**：防止只搜到支持既有印象的材料。
4. **可追溯性**：每条线索都应记录检索入口、状态和后续处理结果。

## 三、史料来源分级

史料检索入口按 source host 与材料性质分级。分级只决定“能否作为回源入口”，不改变正式 `source_title` 的写法。

### A 级：原始史料 / 古籍文本承载站

可作为正式回源入口。

常见类型：

- Wikisource、ctext、可靠古籍库；
- 影印本、点校本、权威数据库；
- 可定位到原书卷次、篇章或段落的文本承载站。

写证据卡和 source document 时必须区分：

```text
source_host = Wikisource / ctext / 影印站 / 古籍库
source_title = 《史记》/《后汉书》/《资治通鉴》等原书
source_location = 卷、篇、页、段落或纪年位置
```

Wikisource 是史料文本承载主机，不等于史书本身；正式 `source_title` 不得写成“维基文库”。

### B 级：百科 / 工具型索引

只作为检索线索，不直接入证据卡。

常见类型：

- Wikipedia、百度百科；
- 人物年表、工具索引页、资料导航页；
- 未直接承载原始史料文本的二手整理页。

Wikipedia 不是正式史源。它可以帮助发现人物、纪年、事件名或原书线索，但正式证据卡应回到 source passage，而不是引用百科条目。

### C 级：二手文章 / 博客 / 摘编

只作辅助线索，不能作为正式证据。

若二手材料提示了可回源事件，应把它转为 `search_logs` / `search_tasks` 线索，并继续寻找 A 级来源或可校验原书段落。无法回源的二手材料不得写成正式证据卡。

## 四、基本资料层级

### 1. 史料线索库

史料线索库记录“可能有用但尚未完成回源裁量”的材料。

允许状态包括：

- 待回源；
- 待核对；
- 待归项；
- 疑似重复；
- 疑似无关；
- 待人工判断。

线索库不得直接入分。

### 2. 原子证据库

原子证据库只收录已回源、可归项、可裁量的材料。

每条原子证据必须有明确来源、短摘、人物、子项、正负方向、候选强度和相邻项切分。

### 3. 证据组裁量库

证据组裁量库收录多条原子证据的综合裁量结论。

它不是新史料，而是对一组原子证据的结构性判断。

### 4. 专题锚点池与对象锚点池

专题锚点池用于保存同类争议、同类证据或同类对象的横向案例。

对象锚点池是专题锚点池的一种用途，用于校准证据涉及对象的权重。对象不限于人物，也可以是指标、空间、机制或事件类型。

对象锚点只服务证据强度校准，不直接替代证据卡，不直接定档，不服务排名，也不单独形成“对象等级 × 责任基础 × 处置强度 × 外溢范围”的计算层。

示例：

- 人物对象：顶级能臣、顶级谏臣、顶级将帅、顶级佞臣、酷吏、近幸。
- 指标对象：粮价、户口、人口增长率、仓储、流民规模、战损比。
- 空间对象：关中、河北、江南、河套、辽东、战略通道、都城圈。
- 机制对象：纳谏、纠错、诏令反转、制度覆盖、监察反馈、长期授权。

## 五、史料上下文进入证据链

对齐 `史料上下文管理机制.md` 后，检索、回源和入卡的最低边界如下：

```text
search_logs / search_tasks
  只保存检索入口、线索、待回源状态、拒绝原因和下一步动作；不得直接入分。

source_documents
  保存史源文档元信息、版本、URL、host、抓取状态和规范位置；不保存证据裁判。

source_passages
  保存可定位段落、原文、规范化文本、卷次位置、前后段指针和解析状态；是全文/段落检索核心。

evidence_source_links
  保存 evidence_id 与 passage_id 的多对多关系，包含 primary_quote、context、counter_context、corroboration、weakening、adjacent_item_split 等引用角色。

evidence_cards
  只保存短摘、解释、归项、方向、候选强度、裁判状态和相邻项切分；不保存大段全文。
```

当前 JSONL 过渡期仍允许 `sources.jsonl` 与 `evidence_cards.source_id` 作为兼容引用。进入 PostgreSQL 原型后，正式关系应由 `evidence_source_links` 指向一个或多个 `source_passages`。

### quote / context 边界

```text
quote_short = 证据短摘。
quote_context = 过渡期人工审核上下文摘录，不是全文存储层。
context_summary = 上下文作用说明，不替代原文段落。
source_passages = 未来全文/段落检索核心。
```

上下文不足时不得直接入正式评分。只有检索线索的材料进入 `search_logs` / `search_tasks`；已定位史源但段落不足的材料进入 review queue；主证、上下文、反证、削弱证或相邻项切分材料通过不同 `link_role` 挂到同一证据链。

## 六、五种检索方式

### 1. 项目驱动检索

项目驱动检索以大项/子项规则为入口。

每启动一个子项，应先根据以下材料生成项目检索包：

- 项目定义；
- 子项边界；
- 标尺；
- 证据裁量规则；
- 正负证触发模块；
- 相邻项切分规则；
- 最小对象锚点池。

项目驱动检索的优点是精确、可控、便于横向比较。

缺点是容易被既有规则和关键词限制，漏掉未预想到的材料。

适用场景：

- 子项启动；
- 定向补卡；
- 横向矩阵填空；
- 已知缺口修补。

### 2. 人物驱动检索

人物驱动检索以某个君主为入口，扫描其相关纪、传、通鉴段落、专题材料和后续评价。

它的目标不是把一个人的所有史料直接放入证据卡，而是建立“人物史料线索池”。

人物线索池应记录：

- 可能涉及哪些项目；
- 是正证、负证还是反转材料；
- 是否需要回源；
- 是否可能触发裁判模块；
- 是否可能成为强证或极证候选；
- 是否涉及高价值对象锚点。

人物驱动检索的优点是召回率高，能发现项目关键词未覆盖的材料。

缺点是工作量大，且容易把人物总体光环带入各子项。

适用场景：

- 核心候选人物；
- 高位档候选人物；
- 强争议人物；
- 正负证明显不平衡的人物；
- 准备进入最终定档前的复核。

### 3. 反向检索

反向检索用于防止正反馈和光环化。

任何人物拟进入高位档，或某一子项拟给强档/极档时，都必须进行反向检索。

基本规则：

- 正证强时，查同项负证；
- 负证重时，查反转材料；
- 单项强时，查相邻项切分；
- 极级候选时，查反例、限制条件和同类锚点；
- 总体印象强时，查是否存在被忽略的结构性弱点。

反向检索不等于为了否定而否定，而是为了确认强证是否稳固。

### 4. 专题横向检索

专题横向检索以事件类型、问题类型或对象类型为入口。

它用于校准同类证据强度，避免单人单案孤立判断。

例如：

- 判断“杀功臣”强度时，横看刘邦、朱元璋、刘秀、刘彻、赵匡胤等；
- 判断“容谏”强度时，横看李世民、刘恒、刘秀、胤禛等；
- 判断“民生崩坏”强度时，横看户口、赋役、饥荒、财政透支等同类材料；
- 判断“战略要地”强度时，横看关中、河北、江南、河套、辽东等空间对象。

专题横向检索不必每个子项都开，但高频争议和高价值对象应沉淀为专题锚点或最小对象锚点。

### 5. 史源驱动检索

史源驱动检索以某一类原始史料为入口，例如：

- 本纪；
- 列传；
- 志；
- 表；
- 《资治通鉴》相关卷；
- 会要、政书、制度史材料；
- 墓志、诏令、奏议等。

史源驱动检索适合在以下情况下使用：

- 项目关键词不稳定；
- 人物材料分散；
- 需要系统扫一段时期；
- 需要核对原典上下文；
- 需要防止只搜关键词导致漏读。

史源驱动检索通常作为项目驱动和人物驱动的补充。

## 七、对象锚点池的建立时机

对象锚点池随项目启动而建，随证据裁量而扩，随阶段收束而沉淀。

不预建全体系对象库，不建立平行评分系统。

### 1. 项目启动时

每个子项启动时，只建立“最小对象锚点池”。

最小对象池通常包括：

```text
顶级正向锚点
普通/中等锚点
负向极端锚点
争议/边界锚点
```

### 2. 执行过程中

只有当对象层级会影响证据候选强度时，才标记对象锚点。

普通弱证、中证、重复材料和低价值线索，不要求全部标对象锚点。

### 3. 阶段收束时

稳定、可复用的对象锚点可沉淀到 `data/thematic_anchors.jsonl`。

临时、争议或只服务当前对话的对象判断，可保留在 PR 说明、批次文件或导出视图中，不必长期入库。

## 八、非数据化对象的受控经验锚定

部分对象难以立即数据化，例如顶级能臣、顶级谏臣、顶级佞臣、战略枢纽、制度机制成熟度等。

这类对象允许先采用受控经验锚定，但必须满足四个条件：

1. **共识级别**：标明是高共识、中共识还是争议锚点。
2. **本项相关性**：说明对象为何影响当前子项，而不是对象本身有名。
3. **相邻项风险**：说明哪些内容不能回填本项。
4. **可修正状态**：使用 `active`、`provisional`、`disputed`、`superseded` 等状态。

争议对象不得作为强证核心锚点，只能作为边界锚点或待复核锚点。

## 九、推荐工作流

### 第一步：项目启动检索

每个子项启动时，先建立项目检索包。

项目检索包应包含：

- 本项正证关键词；
- 本项负证关键词；
- 反转材料关键词；
- 相邻项切分关键词；
- 高风险触发模块关键词；
- 重点人物名单；
- 最小对象锚点池；
- 对象锚点是否需要后续沉淀的判断。

### 第二步：人物线索扫查

对核心人物建立人物线索池。

线索池只记录“可能有用”的材料，不急于定强度。

人物线索应标记状态：

- `lead_only`：只有线索，未回源；
- `source_review_pending`：已定位来源，待核；
- `source_verified_candidate`：已回源，可转证据卡；
- `rejected_irrelevant`：不归本项；
- `rejected_duplicate`：重复材料；
- `needs_human_review`：需人工判断。

### 第三步：项目定向回源

从项目检索包和人物线索池中抽取最相关材料，进行回源。

只有完成回源的材料，才能进入原子证据卡。

### 第四步：反向检索

对以下情况强制反向检索：

- 拟进入强正、强负；
- 拟进入极正、极负；
- 正负证明显不平衡；
- 人物总体历史地位很高；
- 证据主要来自后世评价而非原始事件；
- 已知存在争议或反转；
- 对象锚点影响候选强度。

### 第五步：专题横向补查

若某类证据或某类对象反复出现，或会影响多个候选人的横向强弱，应建立专题锚点池或最小对象锚点池。

专题锚点池先服务裁量，不直接服务排名。

### 第六步：进入裁量体系

完成回源、归项和反向检索后，材料进入证据裁量流程：

```text
原子证据卡
→ 五轴裁量
→ 触发式裁判模块
→ 证据组裁量结论
→ 净证据池
→ 自动结算规则敏感点清单
→ 自动结算草案
→ 规则级人工复核
```

规则级人工复核不再逐人逐条回看全部材料，而是只核对自动结算是否正确命中了抽象规则。

## 十二、强制反向检索规则

以下情况不得跳过反向检索：

1. 拟给强正或极正；
2. 拟给强负或极负；
3. 单一人物正证过密、负证稀少；
4. 单一人物负证过重、反转材料未查；
5. 史料来自高度概括评价；
6. 评价对象具有强历史光环；
7. 裁量结论拟作为横向锚点；
8. 对象锚点拟作为强度校准依据。

## 十三、禁止事项

- 不得把线索库材料直接入分；
- 不得只按已有规则关键词搜索而不做反向检索；
- 不得只搜正证不搜负证；
- 不得只搜负证不搜反转；
- 不得把人物整体评价直接带入子项；
- 不得因某人总体强而降低检索强度；
- 不得因材料多而跳过回源；
- 不得因单个关键词无结果就判定无证据；
- 不得将后人注解、现代括号说明、二手总结直接等同于原始史料；
- 不得把对象锚点当作对象本身的综合评分或排名。

## 十四、与现有数据文件的关系

当前可继续使用 `data/search_logs.jsonl` 作为线索库入口。

后续若扩展数据结构，可考虑增加或明确以下字段：

- `search_mode`：项目驱动、人物驱动、反向检索、专题横向、史源驱动；
- `query_profile_id`：检索包编号；
- `target_person`；
- `target_item`；
- `candidate_polarity`；
- `lead_status`；
- `source_review_status`；
- `linked_evidence_ids`；
- `rejection_reason`；
- `next_action`。

对象锚点当前不强制扩展 search_log schema。若需要记录，可先写入 `trigger_family`、`query_terms`、`result_summary` 或 PR 说明；若进入证据卡/证据簇，则优先作为轻量标签保留，而不是另建独立打分轴。

本讨论版只提出方法，不要求立即修改 schema、validator 或既有数据。

## 十五、执行原则

轻量人物可项目驱动为主；核心人物必须人物驱动补扫；高位候选必须反向检索；争议类型必须专题横向补查。

最终目标不是无限扩充材料，而是保证：

- 关键正证不漏；
- 关键负证不漏；
- 反转材料不漏；
- 横向锚点可比；
- 对象锚点可解释、可修正、可追溯；
- 每条入分证据都可回溯到检索入口和原始史料。

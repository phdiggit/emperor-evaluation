# 人物画像共同数据与发布合同

> `PROFILE-DATA-V1.2`。本文供数据维护使用，规定字段、入口和发布方式；怎样评价人物仍看总合同及各轴规则。

## 1. 权责层级

| 层级 | 正式位置 | 责任 |
|---|---|---|
| 项目注册 | `config/project.yml:profile_assessment` | 唯一登记轴顺序、合同、版本、机器入口、阅读入口和审计入口 |
| 共同语义 | [画像总合同](../../项目总纲/皇帝人物画像评估体系合同.md) | 共同证据、归责、跨轴去重和档位投影 |
| 执行合同 | [工作流](01-画像全池工作流合同.md)、[校准](02-画像校准与首轮校准合同.md)、[外部对照](03-画像外部印象对照合同.md)、[输出](04-画像机器与阅读输出合同.md)、[正式验收](05-画像轴级正式验收合同.md) | 分离执行顺序、校准、对照、输出和启用门禁；不另立评分真源 |
| 轴内语义 | 本目录各轴规则 | 该轴命题、主要入口、专属准入、反例和例外 |
| 正式裁决 | `docs/评分结算/人物画像/{axis}/`下的正式JSON | 当前逐人档位、位置、雷达值和正式依据的唯一机器真源 |
| 入口清单 | `docs/评分结算/人物画像/00-已结算轴正式入口.json` | 由项目注册投影的发现、状态和审计入口，不另立裁决 |
| 阅读视图 | 与正式JSON同名的Markdown | 确定性生成的阅读层，可做明确标注的篇幅压缩，不得改变正式值或结论 |
| 审计材料 | manifest登记的审计JSON | 覆盖、引用、密度和门禁反查，不得成为第二份档位来源 |

路径和顺序只在`config/project.yml`登记，manifest是生成的入口清单。JSON可按朝代分片，统一用`load_json`读取完整内容。

## 2. 版本和轴类型

版本字段含义不可互换：

| 字段 | 所在层 | 含义 |
|---|---|---|
| `profile_assessment.contract_version` | 项目配置/manifest | 共同画像政策合同版本 |
| `axis_contract_version` | 轴注册/manifest | 单轴语义合同版本；只因该轴规则变化而递增 |
| `payload_schema_version` | 轴注册/manifest | 正式JSON载荷 schema；对应正式JSON的`schema_version` |
| `reader_view_mode` | 轴注册/manifest | 阅读视图生成方式；当前正式值为`DETERMINISTIC_GENERATED` |

现行九轴的`axis_kind`均为`DIRECT_PROFILE_AXIS`，直接评价本人，不从其他体系分数换档。

`authority_mode = FORMAL_JSON_SOURCE`表示当前裁决存于正式JSON，不授权程序自动改档。

## 3. 轴注册的最小字段

每个`settled_axes.{axis_code}`至少登记：

```yaml
name: 轴名称
contract: docs/分项规则/人物画像轴/{axis}.md
axis_contract_version: FORMAL-V1.0
payload_schema_version: profile-axis-formal-settlement-v1
axis_kind: DIRECT_PROFILE_AXIS
authority_mode: FORMAL_JSON_SOURCE
reader_view_mode: DETERMINISTIC_GENERATED
json: docs/评分结算/人物画像/{axis}/正式结算.json
markdown: docs/评分结算/人物画像/{axis}/正式结算.md
verify_command: profile-{axis}-verify
audit_jsons:
  - audit_kind: UNIT_DISPOSITION
    path: {axis}/主要入口单元处置审计.json
```

`contract`、`json`、`markdown`相对于仓库根目录。`audit_jsons`每项含`audit_kind`和`path`，其中path相对于画像正式入口目录，并以轴目录开头，如`C3/28-...json`。各轴维护方式可以不同，以上共同字段不能省略。

## 4. 正式记录与父链

共同记录外壳至少要能稳定连接：

- 身份：`ruler_id`、`ruler_name`、`polity`、`task_code`；
- 决策：`axis_grade`、`position`、`score_100`、`radar_value`、`axis_evidence_level`、`output_mode`、`confidence`、`score_status`；
- 依据：`typical_pattern`、`counterpattern`、`grade_basis`、`position_basis`、`limitations`、轴内相关性和正式状态；
- 证据：轴内父链、方向、强度、归责、机制、过程和可反查定位；
- 复核：适用性、反例、阶段/密度/冲突复核及其审计引用。

### 共同文本字段职责

文字直接说明当前裁决，五个字段各答一个问题：

| 字段 | 写什么 |
|---|---|
| `typical_pattern` | 本人通常怎样判断或行动，最有代表性的表现是什么。 |
| `counterpattern` | 哪些事实能修正或挑战上述概括；不一定是负面，低档人物的有效表现也可以。 |
| `grade_basis` | 为什么属于当前大档。 |
| `position_basis` | 为什么在该档的LOW/MID/HIGH，不重复整段定档理由。 |
| `limitations` | 证据、本人责任、阶段、来源或未解决问题对结论有什么限制。 |

用人物事实作解释，不用审计状态或编号代替。清理文字不改分数、档位、置信度和裁决方向，也不让阅读摘要覆盖正式字段。

计分依据、代表依据和计分引用须来自同一有效集合。轴外或背景材料放`non_scoring_observations`，保留来源和处置理由。同一能力过程用`capability_episode_ref`合并，别名放`source_alias_parent_ids`；M1可以另存`phase_evidence`，但阶段行数不当作独立过程数。

同轴比较写在当前记录的`horizontal_calibration`，引用人物ID并说明证据异同，不拿对方分数换算本人成绩，也不要求旧报告随新裁决改写。

新载荷使用`parent_chains`保存完整过程，`representative_parent_ids`只保存展示所选ID；不要再复制完整对象到`representative_parent_contexts`。`source_refs`保留完整来源，`direct_process_refs`或`cycle_anchor_refs`保留过程定位，不能互相覆盖。

现有`parents`、`parent_ref`等旧字段在该轴下次正式维护时按上述含义映射，不因迁移改分。事件ID`profile_episode_id`与过程ID`parent_id/parent_ref`分开，并通过事件引用或来源保持可追溯；旧材料缺事件ID时标明缺口，不用人物ID或日期临时顶替。

### 4.2 跨轴路由闭环

`route_handoff`只说明材料转给哪个轴，不另存档位。每条转交有两种完成状态：

- `CLOSED`：`target_parent_ref`能在目标轴正式记录中找到；旧别名先对应到正式`parent_id`。
- `EXPLICITLY_FROZEN`：尚无稳定目标时，清空活动`target_parent_ref`，写明`freeze_reason`和`reopen_condition`；冻结不计入目标轴，也不改档。

对照表列出源轴、源过程、目标轴及目标过程或冻结理由。只有单位级`AXIS_OUT_WITH_REASON`而没有目标过程的，单列说明，不能当作已经转交完成。

## 5. 阅读视图合同

阅读视图可以翻译字段、合并重复说明、选择代表材料，但须标明节选并能回到完整JSON。各轴按登记的`reader_view_mode`生成。

不得改变分数、等级、状态或理由方向，不把节选冒充全部来源，不从阅读页推导跨轴分数，也不把阅读摘要写回正式裁决。

## 6. 审计和变更闭环

只维护当前裁决及仍承担史源、归责或去重作用的材料。历史看Git，临时诊断放`.tmp/`，不为旧批次报告建立同步要求。

| 改什么 | 同步什么 |
|---|---|
| 评价规则 | 对应轴合同与`axis_contract_version`，检查受影响轴和下游。 |
| 人物裁决 | 正式JSON或明确的局部裁决源，重建Markdown并运行轴验证。 |
| 入口或路径 | 先改`config/project.yml`；单轴用`profile-manifest --axis {axis} --write`，再验入口。注册表本身变化才全量生成。 |
| 数据结构 | 更新`payload_schema_version`、字段检查和迁移；不靠修改分数完成迁移。 |
| 展示 | 修改生成器及对应展示检查，不改裁决。 |

共同合同、schema、轴边界或高风险规则变化才扩展到全池，普通局部维护按影响检查。结算与验证保持离线、确定性，不使用模型、网络或数据库。

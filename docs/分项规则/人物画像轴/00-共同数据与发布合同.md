# 人物画像共同数据与发布合同

> `PROFILE-DATA-V1.1`；本文只规定八轴共同的数据、入口、版本和发布边界，不定义任何轴的评价算法。轴内语义与准入仍以各轴规则为准。

## 1. 权责层级

| 层级 | 正式位置 | 责任 |
|---|---|---|
| 项目注册 | `config/project.yml:profile_assessment` | 唯一登记轴顺序、合同、版本、机器入口、阅读入口和审计入口 |
| 共同语义 | [画像总合同](../../项目总纲/皇帝人物画像评估体系合同.md) | 共同证据、归责、跨轴去重、档位投影和不设画像总分 |
| 执行合同 | [工作流](01-画像全池工作流合同.md)、[校准](02-画像校准与首轮校准合同.md)、[外部对照](03-画像外部印象对照合同.md)、[输出](04-画像机器与阅读输出合同.md)、[正式验收](05-画像轴级正式验收合同.md) | 分离执行顺序、校准、对照、输出和启用门禁；不另立评分真源 |
| 轴内语义 | 本目录各轴规则 | 该轴命题、主要入口、专属准入、反例和例外 |
| 正式裁决 | `docs/评分结算/皇帝人物画像/{axis}/`下的正式JSON | 当前逐人档位、位置、雷达值和正式依据的唯一机器真源 |
| 入口清单 | `docs/评分结算/皇帝人物画像/00-已结算轴正式入口.json` | 由项目注册投影的发现、状态和审计入口，不另立裁决 |
| 阅读视图 | 与正式JSON同名的Markdown | 确定性生成的阅读层，可做明确标注的篇幅压缩，不得改变正式值或结论 |
| 审计材料 | manifest登记的审计JSON | 覆盖、引用、密度和门禁反查，不得成为第二份档位来源 |

`config/project.yml`是路径和顺序的唯一注册源；manifest不得反向成为配置源。正式JSON可以按朝代分片存储，但`load_json`重建后的逻辑载荷必须保持上述正式结构。

## 2. 版本和轴类型

版本字段含义不可互换：

| 字段 | 所在层 | 含义 |
|---|---|---|
| `profile_assessment.contract_version` | 项目配置/manifest | 共同画像政策合同版本 |
| `axis_contract_version` | 轴注册/manifest | 单轴语义合同版本；只因该轴规则变化而递增 |
| `payload_schema_version` | 轴注册/manifest | 正式JSON载荷 schema；对应正式JSON的`schema_version` |
| `reader_view_mode` | 轴注册/manifest | 阅读视图生成方式；当前正式值为`DETERMINISTIC_GENERATED` |

`axis_kind`区分：

- `DIRECT_PROFILE_AXIS`：直接评价本人能力、行为或集团关系的轴；
- `INTEGRATED_PROFILE_AXIS`：在明确上游正式事实接口上进行独立语义统合的轴。当前M3属于此类，不得把上游分数直接相加或一对一转档。

`authority_mode = FORMAL_JSON_SOURCE`表示正式JSON是当前裁决入口；它不表示程序可以自动重裁。没有明确授权时，程序只能生成阅读视图或报告，不能改写正式档位。

## 3. 轴注册的最小字段

每个`settled_axes.{axis_code}`至少登记：

```yaml
name: 轴名称
contract: docs/分项规则/人物画像轴/{axis}.md
axis_contract_version: FORMAL-V1.0
payload_schema_version: profile-axis-formal-settlement-v1
axis_kind: DIRECT_PROFILE_AXIS
authority_mode: FORMAL_JSON_SOURCE
reader_view_mode: DETERMINISTIC_GENERATED
json: docs/评分结算/皇帝人物画像/{axis}/正式结算.json
markdown: docs/评分结算/皇帝人物画像/{axis}/正式结算.md
verify_command: profile-{axis}-verify
audit_jsons:
  - audit_kind: UNIT_DISPOSITION
    path: {axis}/主要入口单元处置审计.json
```

`audit_jsons`中的每项都必须包含`audit_kind`和`path`；`path`统一相对于画像正式入口目录，并且必须以所属轴目录开头（例如`C3/28-...json`），不得混用“轴目录相对”和“画像入口目录相对”两种基准。`contract`、`json`、`markdown`等项目注册路径统一相对于仓库根目录。M3可额外声明正式输入范围和局部维护方式，但不能省略共同字段。

## 4. 正式记录与父链

共同记录外壳至少要能稳定连接：

- 身份：`ruler_id`、`ruler_name`、`polity`、`task_code`、实际权力窗口；
- 决策：`axis_grade`、`position`、`score_100`、`radar_value`、`axis_evidence_level`、`output_mode`、`confidence`、`score_status`；
- 依据：`typical_pattern`、`counterpattern`、`grade_basis`、`position_basis`、`limitations`、轴内相关性和正式状态；
- 证据：轴内父链、方向、强度、归责、机制、过程和可反查定位；
- 复核：适用性、反例、阶段/密度/冲突复核及其审计引用。

### 4.1 统一实际权力窗口

`actual_power_window`的日期边界只读取规范人物池`config/common/canonical-ruler-pool.json`的当前值，八轴正式JSON必须逐人物同步同一边界，不得按轴命题自行缩短或延长。轴记录可以保留不改变起止边界的说明性限定，但不得借后缀制造第二套窗口；窗口外的共享、低自主和归责差异放在阶段、父链或限制字段中。窗口真源的修订先写入`config/common/canonical-ruler-admission-adjudications.yml`，保存`basis`和可反查`evidence_refs`，再重建规范池并同步八轴与阅读汇总。

创业型或实际主导型人物在称帝前已经实际主导创业、军政、政权奠基或最高责任中心的阶段，纳入共同窗口；仅有从属军权、有限授权、名义继承或被摄政/强臣架空的阶段，不自动纳入。共享权力、低自主、从属阶段和窗口内的阶段差异必须在阶段代码、父链归责或限制字段中表达，不能通过缩短共同窗口表达。

窗口扩展只扩大可观察范围，不构成升档、降档、补证完成或雷达值变化的自动理由；窗口同步与人物裁决分离审计。

轴可拥有不同的`axis_payload`，但不得用轴特有字段替代共同决策字段。未来新载荷使用以下语义分离：

1. `parent_chains`保存完整的轴内父链；
2. `representative_parent_ids`只保存阅读层要展开的父链ID；
3. 完整父链对象不得复制到`representative_parent_contexts`；
4. `source_refs`保存完整来源集合，`direct_process_refs`或`cycle_anchor_refs`保存可反查的过程锚；二者不可因展示需要互相覆盖。

尚未完成字段迁移的正式快照中的`parents`、`representative_parent_contexts`、`parent_ref`等字段属于兼容形状。轴被下一次正式维护时，先按本合同映射到上述共同语义，再修改裁决；兼容映射本身不改变分数。已完成迁移的正式载荷使用`parent_chains`与`representative_parent_ids`，其余轴按各自正式维护窗口迁移。

`profile_episode_id`属于输入证据单元的稳定事件ID；`parent_id`/`parent_ref`属于轴内聚合父链ID，二者不可混用。正式父链必须通过`episode_refs`、`source_refs`或直接过程锚保持可反查关系。没有稳定事件ID的旧登记应标为兼容缺口，不得临时以人物ID或日期冒充。

### 4.2 跨轴路由闭环

`route_handoff`只记录轴外处置，不是第二份档位来源。每条正式路由必须进入终态：

- `CLOSED`：`target_parent_ref`必须在声明的目标轴正式父链中存在；旧别名只能在整改时规范为可反查的正式`parent_id`。
- `EXPLICITLY_FROZEN`：当前快照没有稳定目标父链时，必须清空活动`target_parent_ref`，同时保留`freeze_reason`与`reopen_condition`；冻结不把事实计入目标轴，也不自动改变任何档位。

全池对照表登记源轴、源父链、目标轴、目标父链或冻结理由；单位级`AXIS_OUT_WITH_REASON`而没有父链路由的记录单独登记为无父链轴外处置，不得被默认为已完成目标轴承接。

## 5. 阅读视图合同

阅读视图可以：

- 将字段名翻译成面向读者的中文；
- 合并重复说明，压缩来源展示，并明确标注“节选/完整内容见正式JSON”；
- 按轴专门结构展示M1登记、M3轨迹或其他已登记`reader_view_mode`内容。

阅读视图不得：

- 改变`axis_grade`、`position`、`radar_value`、证据等级、状态或裁档理由的方向；
- 把阅读层摘要反写正式JSON；
- 把来源节选伪装成完整来源集合；
- 通过阅读页推导画像总分、轴内排名或综合榜。

## 6. 审计和变更闭环

- 规则变化：更新对应轴合同和`axis_contract_version`，运行受影响轴及下游检查；只有共同合同、schema、轴边界或高风险规则变化才做全池复核；
- 实际窗口变化：先更新规范池窗口裁决与共同合同，再同步八轴`actual_power_window`、八轴汇总和相关展示消费者；窗口同步本身不得改写任何轴档位、位置、分数或雷达值，并须运行全池窗口一致性审计；
- 正式裁决变化：只改正式JSON或其明确的局部patch源，重新生成同名Markdown并运行轴级验证器；
- 入口或路径变化：先更新`config/project.yml`，单轴变化使用`profile-manifest --axis {axis} --write`刷新该轴；只有注册表本身变化才做全量生成，再运行`project-entries-verify`；
- schema变化：递增`payload_schema_version`，更新共同字段检查和迁移兼容逻辑，不以修改分数常量代替迁移；
- 展示变化：只改阅读生成器及视图测试，不触碰正式裁决。

所有变更均保持离线、确定性、无模型、无网络、无数据库写入；局部改动按影响范围验证。

# V3 教训与 V4 约束

> 状态：`review_ready`  
> 目的：把 V3 的失败模式转化为 V4 的结构约束，而不是继续记录修补过程。

## 1. V3 中被验证为正确的方向

以下方向继续保留：

- 史源优先，不能凭模型记忆直接评分；
- 原子事实与规则判断分离；
- 人物身份、事件身份和规则版本显式化；
- 多来源证据需要汇聚；
- 计分尽可能确定性执行；
- 正负证、排除理由和 lineage 必须可审计；
- 模型不得直接发布正式分数。

V4 不否定这些原则，而是重新安排它们的核心对象和执行顺序。

## 2. 核心失败模式

### 2.1 原子 claim 承担了过多职责

V3 中 claim 同时接近：

- 证据存储单位；
- 调度单位；
- 覆盖度单位；
- 去重单位；
- 规则路由单位；
- 计分入口。

结果是原文中的完整叙事被过早拆散，后续 candidate、binding、factorization 又反复拼回同一事件。

**V4 约束**：`Assertion` 只表示来源断言；`HistoricalEpisode` 才是调度、语义去重和事件型规则投影的核心单位。

### 2.2 canonical event 建立得太晚

跨来源、跨措辞的同一事件在上游形成多条独立记录，后面再靠 event group 收束，导致物理记录和语义主体长期错位。

**V4 约束**：断言接受后立即进入 episode reconciliation；未完成事件身份的断言不得直接进入规则消费。

### 2.3 全表重建造成大范围失效

material 或下游按物理 ID 全量重建时，补一条证据可能导致 candidate、binding、judgment 和 score 全部失效。

**V4 约束**：

- 正常路径只允许按 changed IDs 增量更新；
- 语义版本和证据版本分离；
- 新增同义证据只更新 evidence version；
- 全表重建只能是灾难恢复工具，必须独立批准和审计。

### 2.4 同一事件被智能体重复理解

抽取、候选复核、身份、因子和画像阶段反复读取同一段史料并重新判断。

**V4 约束**：建立通用事件语义结果和规则判断缓存；模型只进入歧义慢通道，清晰事件走确定性快通道。

### 2.5 覆盖度概念混杂

“claim 覆盖不足”曾同时指：

- 史源没抓到；
- 事件没识别；
- 人物没对上；
- passage 丢失；
- event/material 没消费；
- binding/factor/score 没完成。

**V4 约束**：覆盖报告强制拆为：

```text
source_coverage
episode_recall
consumption_integrity
```

任何总状态必须能下钻到具体阻断阶段。

### 2.6 canonical person 与评估上下文混淆

同一人物的“早期/晚期/任用阶段”曾被创建为独立人物；同一人物跨 target 也可能重复计数。

**V4 约束**：

- canonical person 全局唯一；
- 时期、皇帝、官职和事件角色属于关系或上下文；
- 人物集合型规则按 canonical person 去重；
- 创建/合并人物必须经过 identity gate。

### 2.7 规则输入类型被强行统一

`team_building` 本质上是人物集合快照，却曾被塞入单条 claim/binding 流程。

**V4 约束**：每条规则必须声明 `input_type`、`coverage_unit`、`dedupe_key` 和 `scoring_unit`；事件型、人物快照型和聚合上下文型规则可共享底座，但不共享同一种中间实体。

### 2.8 组件存在不等于状态机闭环

任务领取、claim 落库、event group、人物发现和画像评审曾分别可运行，但失败重试、子进程环境、过期 lease 和阶段完成状态不统一。

**V4 约束**：所有阶段使用持久化任务、lease、attempt、input/output fingerprint、outbox 和可恢复状态；“子进程退出 0”不是业务成功。

### 2.9 文件补丁和跨机器往返成为业务流程

生产链路曾依赖 prompt 文件、last message、patch 恢复、复制到服务器再消费。

**V4 约束**：文件补丁只用于开发和人工审查；生产链路使用结构化接口、Schema 校验和数据库任务结果。

### 2.10 性能问题来自重复工作而非单纯并发

全链重建的长耗时由重复理解、全量选择、细碎批次和远程往返共同造成，提高并发只能局部缓解。

**V4 约束**：先减少模型调用和失效范围，再调整并发；性能预算以“多少工作无需执行”为第一指标。

## 3. V4 十条不可妥协约束

1. HistoricalEpisode 是事件型规则的第一语义主体。
2. Assertion 永远保留来源和原文，不因事件合并被删除。
3. 同一 canonical person 只有一个活动身份。
4. 语义版本与证据版本分离。
5. 每层都有数据库级幂等和唯一门禁。
6. 正常增量不得全表重建。
7. 模型只处理歧义，不承担默认流水线。
8. 判断和评分缓存基于语义与规则版本，不基于易变物理 ID。
9. 覆盖度分三层报告。
10. 无变化重跑零写入、零模型调用。

## 4. V3 资产使用规则

V3 可以提供：

- 失败样本和回归案例；
- 人工裁定过的边界事件；
- 史源候选线索；
- 规则有限值和评分公式的需求来源；
- 性能、重复、漏链和错绑案例。

V3 不可以直接提供：

- V4 正式事实；
- V4 canonical IDs；
- V4 已接受判断或分数；
- V4 Schema、任务状态机和运行配置；
- 未重新回源核验的 claim/material/binding 数据。

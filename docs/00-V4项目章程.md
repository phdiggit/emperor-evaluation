# V4 项目章程

> 状态：`accepted`
> 文档版本：`v2`
> 适用阶段：V4 初始化、三人试点、纵向评分链与配套服务源码收口

## 1. 项目目的

《皇帝综合评价体系评分标准》是 V4 业务事实上的最高驱动文档。HistoricalEpisode、EpisodeRelation、RuleEvidenceUnit、人物画像、智能体裁决和 PostgreSQL 状态机都是为评分标准服务的基础设施，不是项目最终目的。

V4 的目标不是重新包装 V3，而是建立一条可扩展、可审计、可增量运行的历史证据与评分链：

```text
史源内容
→ 可定位段落
→ 来源断言
→ canonical historical episode
→ 规则投影
→ 结构化判断
→ 确定性计分
→ 覆盖与发布门禁
```

V4 需要同时解决三类问题：

1. **历史事实质量**：重要事件能召回、来源可定位、同一事件不重复、不同事件不误合并；
2. **工程可持续性**：新增证据和人物只触发局部增量，不因物理 ID 变化重跑整链；
3. **决策可信度**：规则判断、评分和覆盖结论都可回溯到事件、断言和史源。

## 2. 成功定义

V4 成功不是“脚本可以跑”，而是满足以下性质：

- 同一历史事件跨来源汇聚为一个当前语义主体；
- 新增同义证据不重复计分，也不默认触发模型；
- 无变化重跑不写业务数据、不调用模型；
- 每个正式判断和分数都有完整 lineage；
- 史源覆盖、事件召回、消费完整性分开度量；
- 智能体仅处理规则无法确定的歧义；
- 任一失败阶段可重试，不重跑已成功阶段；
- V3 与 V4 可并行对照且互不写入。

## 4. 非目标

当前阶段不做：

- 全部皇帝迁移；
- 全部七大项实现；
- V3 数据整库迁移；
- V3 分数、排名或判断回填；
- 生产替换、双写或自动切换；
- 通用智能体平台；
- 完备历史知识图谱、完整臣子仕途或覆盖历代官制的一一映射；
- 为与评分无关的细本体强制建立全部 EpisodeRelation；
- 为未来所有可能需求预建大型 Schema；
- 用数量指标强行均衡朝代、人物或档位分布。

## 5. 决策原则

- 正式评分单元采用“最小充分证据”：只要足以完成皇帝归责、权责方向、结果、净收益、重复结算和档位判断，就不得因非评分必要的历史细节缺失而阻断。
- “足够评分”不等于放松史实；对象、行为、皇帝归责、结果方向和史源 lineage 必须严格。
- 新增领域对象、关系类型、Gate 或智能体调用前必须回答：是否改变评分正确性，是否防止重复计分、错误归责或重大漏算，是否显著改善史源追溯；三项均否时不得进入关键链路。
- 业务语义先于表结构。
- 稳定身份先于运行方便。
- 增量和幂等先于批量重建。
- 可解释的阻断先于“尽量跑完”。
- 正确的缺失状态优于伪造完整。
- 规则输入类型按业务本质设计，不强迫所有规则共享同一中间对象。
- 技术实现可以替换，已接受的领域契约和 lineage 不得被无版本覆盖。

## 6. 角色与批准

当前默认决策角色：

- **业务规则批准**：项目负责人；
- **史源与事件接受**：人工审查或明确规则门禁；
- **架构与契约批准**：专门设计审查；
- **生产切换批准**：独立任务、显式授权、可验证回滚。

模型、worker、CI 和脚本都不是批准者。

## 9. V4 配套服务源码治理

### 9.1 适用对象

离线史源缓存服务和 Claim 抽取服务只服务于 V4，是 V4 评分证据链的一部分，不再视为服务器上的外部脚本或 V3 遗留运行资产。两者的活动源码、数据库 migration、测试、服务启动模板和发布清单必须进入 V4 同一 Git 历史；服务器工作目录、`.env`、凭据、DSN、日志和缓存内容不得进入 Git。

服务器当前 `e27bbff94b9c9acabba716191afd7bdc8bac4550` release 已由 Git 提交构建，但源码仍位于从旧冻结点分出的服务分支，属于过渡状态。V4 主线已从 `32dbf817fdb388bb352766f34ddac8b61cc0a678` 开始承载 Source Cache 最小合同纵切，在 `6149569233cbae73b97a4c3032c20fadf638ab1c` 通过其隔离 PostgreSQL、job/lease 与不可变 release Gate；Claim Extractor 又由 `5b19e47c8be77f6db8c79acae4742b26ca2dd518` 完成版本化 profile、v2 application、独立持久化和同类服务器 Gate。两项生产 unit 与指针仍未切换，Claim Extractor 真实模型 provider 仍待同请求 shadow。旧服务分支不得长期作为 V4 服务事实源，也不得整体 merge 或整目录搬入 V4 主线。

### 9.2 目录与职责归属

服务能力按现有 V4 包边界拆入，不新建一套平行架构：

```text
src/emperor_v4/contracts/     请求、响应、错误、版本与 lineage 数据合同
src/emperor_v4/adapters/      Wikisource、模型和外部接口适配；不得决定正式事实或评分
src/emperor_v4/application/   ensure/supplement/extract 等用例编排与幂等流程
src/emperor_v4/persistence/   V4 cache、job、lease、result repository
src/emperor_v4/runtime/       薄 worker/CLI 入口，只装配依赖和报告运行状态
db/migrations/                仅 V4 schema 的幂等 migration
deploy/v4/                    无凭据的 systemd/启动模板与不可变 release manifest
tests/                        按业务不变量组织的离线、契约与少量 opt-in 集成测试
```

不得把现有数千行 worker 原样放进 `application` 或 `runtime`。队列租约、史源发现、原文缓存、passage 切分、Claim 生成、模型调用、结果持久化和发布必须具有可独立测试的边界；worker 入口不得承载这些业务实现。

### 9.3 服务边界

- 史源缓存服务以 `source-cache-contract-v2` 为当前合同，只产生不可变 document、passage、coverage、error 和 provenance；不得产生 Assertion、Episode、Judgment 或 Score。
- Claim 抽取服务以 `assertion-extraction-contract-v2` 为当前合同，只从 passage 产生 Assertion 草案与 linkage 建议；不得接受正式事实、路由正式规则或生成 factor/score。
- 评分需要可以通过版本化 `extraction_profile` 改善召回，例如人物发现链、授权链或结果链；profile 只规定应关注的可复核事实形状，不得携带 Gold 结论、档位或分数。
- 当前服务按 `rule_code == talent_discovery` 增强提示词属于过渡兼容实现。迁入 V4 主线时必须改为显式、版本化的 `extraction_profile`，并证明其他 profile 不受注入。
- Source Cache 成功与 Claim 抽取成功分别记账；下游失败不得回写或污染已接受的缓存版本。

### 9.4 版本、幂等与副作用

每个服务结果至少声明：

```text
contract_version
input_fingerprint
source_policy_version / extraction_profile_version
window_policy_version / extraction_schema_version
model_policy_version（仅 Claim 抽取）
service_release_sha
output_fingerprint
```

- 相同有效输入重跑必须复用结果：史源缓存零重复网络抓取，Claim 抽取零模型调用，两者零重复业务写入。
- 每个写入口必须有 V4 数据库级幂等键；只允许写 V4 cache/job/result 状态，不得写 V3 schema、正式 Assertion 接受表、正式评分或排名。
- 模型输出先经过 Schema、passage lineage 和质量 Gate；模型和 worker 都不是事实批准者。
- 发布物必须由干净 Git commit 构建，记录 commit SHA、文件清单和 archive hash；服务器不得热改源码。回滚只切换到前一不可变 release。

### 9.5 迁入方式与退出条件

服务迁入采用“行为盘点—合同测试—最小移植—影子比对—切换”的顺序：

1. 冻结当前 release 及魏徵等真实响应作为只读回归样本，列出网络、模型、数据库和文件副作用；
2. 先迁共享的 job/lease、fingerprint、result 和发布骨架，再迁史源缓存，最后迁 Claim 抽取；
3. 从旧服务分支选择性提取仍符合 V4 合同的实现，不 merge 分支、不复制 V3 scorer、consumer、人物画像或旧 orchestrator；
4. 新旧实现对同一冻结请求进行 shadow 对比，差异必须归类为合同修复、召回改善、允许格式变化或回归；
5. 新 V4 服务通过门禁后，部署名改为 `emperor-v4-source-cache-worker` 和 `emperor-v4-claim-extraction-worker`，再停止历史命名的 unit。

迁入完成必须同时满足：

- 活动服务源码只来自 V4 当前 Git 历史，服务分支不再承载独立事实源；
- `retrieval_v3` 不再出现在活动包名、数据库 schema、队列名、unit 名或 runtime 路径中；
- 契约 fixture、无变化重跑、局部 refresh、失败重试、lease 恢复和不可变发布均有测试；
- 同一冻结 workset 的 SourcePassage/Assertion lineage 不丢失，且无新增无原文支持事实；
- 快速套件保持离线、零模型、零外部数据库；真实网络、模型与 PostgreSQL 验证保持 opt-in；
- 完成可验证回滚后，方可删除服务器历史 unit 和旧 release 保留策略之外的运行副本。

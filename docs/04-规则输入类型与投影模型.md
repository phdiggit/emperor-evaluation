# 规则输入类型与投影模型

> 状态：`accepted_and_hardened_by_minimum_sufficient_scoring_unit`
> 目标：让规则按业务本质选择输入，不再强迫所有规则走 claim→binding 的同一路径。

## 1. RuleDefinition 必填声明

每条规则必须声明：

```yaml
rule_code:
input_type:
applicability:
coverage_unit:
dedupe_key:
scoring_unit:
factor_schema:
rule_version:
```

缺少任一项不得实现。

## 2. 最小充分评分单元

RuleEvidenceUnit 和其他正式评分输入必须按《皇帝综合评价体系评分标准》的具体指标组织事实，而不是按人物完整履历或历史本体完整性组织。一个评分单元只需可靠回答当前指标所需的有限问题：

- 哪位皇帝作出决定，对象是谁；
- 授予、扩大、转移、削减或终止了什么实质权责；
- 对象产生了什么结果，皇帝是否反馈、纠错或继续授权；
- 皇帝责任是直接、部分还是不存在；
- 该事实是否会与其他评分单元重复结算；
- 全部关键判断能否回溯到 Assertion 与 SourcePassage。

能回答这些问题并保留严格 lineage，即达到“最小充分证据”。不得仅因以下信息不完整而阻断规则 shadow：完整仕途、前后完全相同的官名、所有事件间的细类型 Relation、完整官制知识图谱，或每个 direct relation 唯一落入细粒度枚举。

反向约束保持不变：对象、行为、皇帝归责、权责方向、结果方向和史源真实性不得放松。若方向、归责、结果或重复消费仍不明确，必须失败关闭。

## 3. 四类输入

### 3.1 episode

用于评价单个历史事件或任务链。

典型规则：

- `talent_discovery`
- `appointment_delegation`
- `tolerate_talent`
- `anti_nepotism` 的个案部分

默认对象：HistoricalEpisode + EpisodeParticipant + Evidence links；需要观察长期任用与反馈链时，可消费按同一评分决策弧组织的 RuleEvidenceUnitDraft。EpisodeRelation 只在防止错误归责、重复消费或表达评分必要的授权—结果—反馈联系时建立，不得为了图完整性强制建边，也不得扩大 HistoricalEpisode 边界。

### 3.2 person_snapshot

用于评价某位皇帝在给定时间窗内拥有或使用的人物集合。

典型规则：

- `team_building`

默认对象：RulerPersonSetSnapshot + PersonProfileSnapshot。

### 3.3 aggregate_context

用于评价跨事件、跨人物的稳定制度或选择渠道结构。

可能用于：

- `anti_nepotism` 的长期结构；
- 某些团队功能互补和人才流动机制。

不得为了方便把 aggregate_context 伪造成一条“大 claim”。

### 3.4 episode_graph / rule_evidence_unit

用于共同消费多个 accepted Episode，以及评分确实需要时的 accepted Relation，形成任用、反馈、撤权或因果决策弧。RuleEvidenceUnit 是面向评分指标的主消费单元；同一处分过程中的多项措施可以直接以成员角色进入同一单元，不要求每两项之间都有细关系边。RuleEvidenceUnit 必须绑定 rule version、aggregation policy version 和成员角色。同一 episode 在同一 rule/evaluation context/version 下不能既单独投影，又通过 RuleEvidenceUnit 重复投影。

Relation 的评分必要载荷优先使用 `relation_family + direction + scope + evidence`；`fine_type` 默认可选。粗关系已经足以完成归责、权责方向和重复消费控制时，`fine_type_status` 可记为 `not_required_for_scoring`，不得仅因细类型为空阻断规则 shadow。

## 4. RuleProjection

Projection 是中立对象与规则之间的可版本关系。

核心字段：

- `projection_id`
- `rule_code`
- `rule_version`
- `input_type`
- `input_ref`
- `evaluation_context`
- `applicability_status`
- `projection_payload`
- `semantic_fingerprint`
- `projection_status`

Projection 不复制史源原文，也不改变 Episode。

`appointment_delegation` 首个 shadow 只允许从已通过 Gate 的 RuleEvidenceUnit draft 生成中立 Projection draft。draft 必须保留输入 semantic fingerprint、成员角色、皇帝归责、Assertion lineage 和问题 readiness；不得生成正式 Projection ID，也不得因进入 Projection 层而补写史实、方向或分数。

## 5. 适用性与评分分离

规则处理分两步：

1. **Applicability**：该 episode/快照是否属于当前规则；
2. **Judgment**：若适用，其方向、因子和强度如何。

不适用不是负分，必须记录排除理由，例如：

- 仅有官职，无皇帝任用链；
- 仅有人物结局，无授权结果因果；
- 属于军事结果，但与用人责任无关；
- 属于团队结构，不应作为单事件重复计分。

## 6. 去重键

### episode 规则

推荐：

```text
episode_id + rule_code + rule_version + evaluation_context
```

同一 episode 在同一规则和上下文下只能有一个活动 Projection。

### person_snapshot 规则

推荐：

```text
ruler_id + evaluation_window + person_set_version + rule_code + rule_version
```

### aggregate_context 规则

根据聚合边界定义稳定窗口和成员版本，不得用生成时间作为身份。

## 7. Judgment 缓存

缓存键至少包含：

```text
input semantic fingerprint
+ rule version
+ judgment policy version
+ output schema version
```

以下变化不应默认重判：

- 物理数据库 ID 变化；
- 新增同义证据但语义字段不变；
- 展示摘要变化；
- 生成文件路径变化。

以下变化必须评估失效：

- 事件主体、责任、结果或方向改变；
- 人物身份合并/拆分；
- 规则定义或因子有限值改变；
- 原有证据出现实质冲突。

增量重跑必须以输入 semantic fingerprint 划定局部失效范围：变化单元重建 Projection 并重新审查，未变化单元的 Projection 与 Judgment 缓存应逐字段复用，不得以同批存在其他变化为由整规则重判。当前状态统一见仓库根 `README.md` 与 `config/project.yml`。

首个 Judgment readiness shadow 使用 `person_task_fit / authority_clarity / feedback_handling / attributable_outcome` 四个观察维度，有限值为 `positive_signal / negative_signal / mixed_signal / evidence_gap / not_applicable`。这些 observation 不是已批准的 factor values。任一关键 readiness 仍有 `evidence_gap` 时必须阻断方向，不能把正负信号直接升级为 Judgment。

## 8. 规则间复用与重复结算

多个规则可以观察同一 episode，但每条 Projection 必须说明观察的不同业务属性。

例如：

- 识别人才：`talent_discovery`
- 把人才放到适合任务并产生反馈：`appointment_delegation`
- 允许其表达、保全或修复授权信用：`tolerate_talent`

同一自然语言材料不能因为出现多个关键词就自动在多规则入分。跨规则复用需通过业务边界检查，并在 ScoreContribution 中保留重复结算审计标记。

## 9. 第五项 B 输入映射

| rule_code | input_type | coverage_unit | scoring_unit |
| --- | --- | --- | --- |
| `talent_discovery` | `episode` | 发现/引入事件 | 被发现人才的一次独立识别链 |
| `appointment_delegation` | `episode` / `rule_evidence_unit` | 原子任用事件或任用—反馈图 | 独立事件或去重后的规则证据单元 |
| `team_building` | `person_snapshot` | 皇帝—人物集合 | 一个冻结团队快照 |
| `tolerate_talent` | `episode` | 容谏、保护或伤害事件 | 一次独立表达/安全事件 |
| `anti_nepotism` | `episode` / `aggregate_context` | 个案与结构渠道 | 个案贡献或冻结结构快照 |

首轮 `appointment_delegation` 已完成；`talent_discovery` 已用同一有限因子与 ScoreContribution runner 完成首个 shadow 复用切片，其余规则仍先用契约和样本验证输入类型。

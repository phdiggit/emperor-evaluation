# 智能体边界与成本预算

> 状态：`accepted`
> 原则：智能体是歧义处理器，不是流水线默认执行器。

## 1. 允许解决的问题

- 候选史源和检索词建议；
- 段落中的 Assertion 草案；
- episode merge/split 候选；
- 人物身份歧义；
- 史源冲突提示；
- 责任归因和规则边界的歧义草案；
- 规则无法唯一确定时，从当前 factor schema 的有限 option code 中提出带 Assertion lineage 的档位草案；
- 人工 review worklist；
- shadow 差异解释草案。

所有输出必须结构化并经过规则或人工 Gate。

## 2. 禁止承担的问题

- 发明史源、locator 或原文；
- 直接接受历史事实；
- 静默创建/合并 canonical person；
- 直接决定 canonical episode；
- 自由生成规则因子值；
- 输出因子数值、材料分、ScoreContribution 或任何绕过确定性映射的计算结果；
- 直接写正式分数和排名；
- 直接写生产数据库；
- 以模型总结覆盖来源冲突；
- 决定生产切换。

## 3. 调用前检查

每次调用前必须依次执行：

1. 输入是否已有确定性结果；
2. cache 是否命中；
3. 是否可通过有限规则解决；
4. 是否属于 `config/model-policy.yml` 允许用途；
5. 最小上下文是否足够；
6. 输出 Schema 和允许值是否明确；
7. 失败后是否可重试且不会重复写入。

任一步不满足，不得调用。

## 4. Episode Boundary Review 局部缓存

边界审查先把 passage-specific Assertion 确定性聚成 PropositionCluster，再按 evaluation context、focal person、相邻时间窗和责任域组成 Review Unit。缓存键为：

```text
review unit proposition semantic hashes
+ boundary policy version
+ output schema version
+ model family
```

局部新增证据只失效相关 Review Unit；未变化 unit 必须零模型调用。一次 holdout 或整皇帝只调用一次模型不是优化目标。

## 5. 通用事件语义缓存

推荐缓存：

```text
episode semantic fingerprint
+ semantic version
+ analysis policy version
+ output schema version
```

内容可包括：

- 人物与角色；
- 行动；
- 责任；
- 结果；
- 因果边界；
- 冲突字段；
- 不确定性。

规则投影读取该结果，不为每条 rule 重新理解全部原文。

## 6. Judgment 缓存

```text
projection semantic fingerprint
+ rule version
+ judgment policy version
+ output schema version
```

## 7. Factor Observation 资格门

`appointment_delegation` 的资格输入只包含既有 V4 judge 观察、HistoricalEpisode 摘要、Assertion 摘要与 SourcePassage 定位，以及不带数值的有限 option code 说明。不得向智能体暴露 V3 人工校准、旧 factor proposal、确定性数值映射、材料分或排名。

响应必须完整覆盖冻结 RuleEvidenceUnit，只提交正负 factor material、option code、理由和 Assertion lineage。资格报告再在智能体调用结束后单独读取人工校准 Gold；门槛为档位精确率不低于 85%、正负材料结构 100% 一致、方向错误为零、非相邻档位错误为零。

仓库中的 `contract_fixture_response.json` 来自人工校准，仅验证 Schema、对照器和阈值实现，并明确声明访问过 Gold；它不得产生 `real_agent_qualified=true`。只有未接触 Gold、旧 proposal 和数值映射的 `independent_blind_agent_run` 才能通过资格门。通过后仍只允许进入独立的 shadow scoring review，不得直接写 ScoreContribution、正式分数或数据库。

新的 sealed holdout 必须由 `codex-win` 监管并执行 `collect`。执行审计至少记录 `task_code`、终态、`duration_sec`、`input_tokens`、`cached_input_tokens`、`output_tokens`、`reasoning_output_tokens`、产物是否经 fallback 恢复及 `error_type`；同时读回实际命令中的显式模型参数。任一统计缺失时，即使业务档位达到阈值，也不得标记 `real_agent_qualified=true`。

开发集延迟基准显示：同样处理 4 个 RuleEvidenceUnit，单批耗时 67.544 秒；拆为 2 个双单元并发批耗时 48.747 秒但 token 增加 76.64%；拆为 4 个单单元并发批耗时 30.283 秒但 token 增加 195.44%，且本次档位精确率更低。默认策略因此保持每批最多 4 单元，在全量名单中并发多个四单元批；优化目标以墙钟耗时优先，但质量 Gate 不让位，token 必须继续记录。

物理 ID、文件路径、展示摘要和新增同义证据不应导致缓存失效。

## 7. 初始成本预算

预算是设计门禁，不是对外 SLA。

| 场景 | 模型调用预算 |
| --- | ---: |
| 无变化重跑 | 0 |
| 已知 episode 新增同义证据 | 0 |
| 已知 episode 新增 locator/版本信息 | 0 |
| 清晰的新 episode | 0 次边界审查调用 |
| 未命中 Boundary Review Unit | 每个 unit 最多 1 次；必要时 1 次独立复核 |
| 冲突且影响正式判断 | 最多 2 次模型意见，最终必须人工裁定 |
| 规则明确且 cache 命中 | 0 |

试点总体目标：

- 平均每个新接受 episode 的模型调用不高于 1.5 次；
- 不允许同一 episode 在抽取、候选、factor 和 scorer 阶段重复完整理解；
- 模型 token 与耗时按阶段、episode、命中/未命中分别报告。

## 8. 上下文预算

- prompt 只包含当前任务需要的字段和来源片段；
- 不把完整项目文档、完整人物材料或所有规则全文注入；
- 规则任务只注入当前 rule 的有限值、边界和反例；
- passage 太长时以可定位窗口分段，但保持前后文引用；
- 任何截断都记录原 passage ref 和截断策略。

## 9. 批量执行

- 批次按“独立歧义单元”组织，不按文件路径或物理 ID 随意切；
- 每行有稳定 task/workitem code；
- 每个输出恰好对应一个输入；
- 缺行、重复行或值域错误整批不得落库；
- 失败只重跑缺失 workitems；
- 模型任务不修改源码和数据库。

## 10. 监控

至少记录：

- 调用原因；
- cache 命中率；
- 输入/输出 fingerprint；
- 模型与策略版本；
- token、耗时和重试；
- Schema 验证；
- 人工接受/拒绝；
- 最终是否影响 Judgment 或 Score。

优化优先顺序：

1. 消除不必要调用；
2. 扩大安全缓存；
3. 缩小上下文；
4. 流水化批次；
5. 最后才提高并发。

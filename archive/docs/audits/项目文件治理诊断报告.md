# 项目文件治理诊断报告

本报告对应 Issue #80。它是只读诊断，不是清理 PR。本轮不删除、不移动、不重构业务文件，不改评分规则、证据内容、脚本实现、导出视图或正式结论。

诊断依据包括 `AGENTS.md`、`README.md`、`.gitignore`、`docs/数据规范.md`、`docs/数据层级与批次文件治理规则.md`、`db/schema.sql`、`scripts/build/build_db.py`、`scripts/export/export_md.py`、`scripts/export/export_i5b_auto_adjudication.py`、`scripts/validate/validate_evidence.py`、`scripts/matrix/run_matrix.py`，以及对 `data/`、`data/*_batches/`、`docs/`、`exports/markdown_views/`、`scripts/`、`tests/`、`configs/`、`db/` 的文件树扫描。

## 1. 总体结论

当前 `JSONL -> SQLite -> Markdown` 架构继续合理。`data/*.jsonl` 仍适合作为事实源，`evidence_cache.sqlite` 仍适合作为本地生成运行库，Markdown 继续作为审阅导出层而不是主源。

暂不需要 PostgreSQL、MySQL 等外部数据库。当前仓库不是在线服务，也没有多人在线并发写入、跨进程查询服务或复杂事务压力。引入外部数据库会增加部署、迁移、权限、备份和 PR 审计成本，收益不足。

暂不需要 Redis 或外部缓存。现有缓存需求由本地 SQLite 生成库覆盖，且 `.gitignore` 已明确排除 `evidence_cache.sqlite`。当前瓶颈不是热点查询，也不是在线低延迟访问。

暂不需要消息队列或中间件。项目主要工作流是离线 JSONL 校验、构建 SQLite、导出 Markdown、运行测试，不存在需要异步任务编排的生产流量。

当前主要瓶颈不是机器性能或数据规模，而是 Codex 阅读成本、导出污染风险和文件治理成本。`scripts/export/export_md.py` 已约 1500 行，`exports/markdown_views/` 有 40 个导出文件，`data/*_batches/` 有 29 个 JSONL 批次文件。随着 issue 链条推进，批次层和导出层正在积累，需要先治理职责边界，再考虑实际清理。

## 5. 架构性能边界判断

当前项目不是在线服务。它没有常驻 API、用户请求并发、跨实例共享状态或在线事务。

当前性能瓶颈主要不在并发查询。文件树扫描显示，仓库内主要数据和导出文件规模仍在本地脚本可轻松处理的范围内。真正的风险是人和 Codex 在 PR 中读错、改错、批量重写旧导出，或者让批次文件长期悬挂。

`data/*.jsonl` 仍适合作为事实源。它天然适合 PR diff、人工审阅、ID 追踪和小规模结构化数据治理。

`evidence_cache.sqlite` 仍适合作为本地生成运行库。`db/schema.sql` 已提供表结构与索引，`scripts/build/build_db.py` 可从 canonical JSONL 生成数据库；该 SQLite 文件不应进 Git。

外部数据库、缓存、中间件暂不建议引入。除非未来出现以下条件，否则不应升级：

- canonical JSONL 增至非常大，且本地校验、构建、导出明显变慢；
- 多人并发编辑成为常态，需要事务、锁、权限或冲突解决；
- 需要在线 API、跨工具服务或长期运行的查询服务；
- 需要复杂全文检索、多维索引、模糊查询或跨实体图谱查询；
- PR diff 已无法承载主数据审计，需要数据库迁移审计或专门审阅界面；
- 导出视图生成需要排队、增量构建或跨任务调度。

在这些条件出现前，优先投入文件治理、脚本拆分、指定导出、批次归档策略和测试约束。

## 7. 不建议立刻做的事

- 不要第一轮直接删除文件。
- 不要第一轮大规模重构。
- 不要把 JSONL 主源迁移到数据库。
- 不要引入缓存或中间件。
- 不要把导出视图当主源。
- 不要在治理 PR 中动评分规则、证据内容或正式结论。
- 不要把批次文件是否可删交给文件名直觉判断。
- 不要运行会批量重写旧导出的命令后把无关导出带入 PR。
